  • J01

    Java has eight primitives (byte, short, int, long, float, double, char, boolean) which hold values directly on the stack or inline in an object, and matching wrapper classes (Integer, Long…) which are real objects on the heap. Autoboxing is the compiler silently converting between them: Integer x = 5 becomes Integer.valueOf(5), and int y = x becomes x.intValue().

    The interview trap is the Integer cache. Integer.valueOf returns cached, shared instances for values in −128..127, so == (reference comparison) accidentally works in that range and silently breaks outside it. This is why you compare boxed values with .equals(), always.

    Two more consequences worth stating: unboxing a null wrapper throws NullPointerException at a line that looks arithmetic, and boxing in a hot loop allocates millions of short-lived objects — which is why the primitive-specialized types (IntStream, LongAdder, int[]) exist.

    Java
    Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b); // true  - both from the cache
System.out.println(c == d); // false - two distinct objects
System.out.println(c.equals(d)); // true - correct comparison

Map<String,Integer> m = new HashMap<>();
int v = m.get("missing"); // NPE: unboxing null
    Follow-ups they will ask

    Why does the cache exist at all, and can you change its range?

    Small integers dominate real programs (loop counters, ids, flags), so caching them removes most boxing allocation. The upper bound is tunable with -XX:AutoBoxCacheMax; the lower bound of −128 is fixed. Never write code that depends on it.

    Where does autoboxing bite in collections?

    List<Integer>.remove(1) removes index 1, but remove(Integer.valueOf(1)) removes the value 1 — overload resolution prefers the primitive. Also, a Map<Long,…> queried with an Integer key never matches, because equals checks the class.

    What is the cost of Integer vs int in memory?

    An int is 4 bytes; an Integer is a 16-byte object header plus the 4-byte field plus an 8-byte reference to it — roughly 6x. That is why int[] beats List<Integer> for large numeric data.

  • J02

    Java is always pass-by-value — there is no pass-by-reference. What confuses people is that for objects, the value being copied is the reference. The method gets its own copy of the pointer, aimed at the same object.

    So a method can mutate the object you passed (both references point at the same heap object), but it cannot reassign your variable — reassigning only changes the method's private copy of the pointer. This is exactly why a swap(a, b) method is impossible in Java.

    Say it precisely in an interview: the reference is passed by value. Saying "objects are passed by reference" is the wrong answer even though it predicts most behaviour correctly.

    Java
    static void mutate(StringBuilder sb) { sb.append("!"); }   // caller sees it
static void reassign(StringBuilder sb) { sb = new StringBuilder("x"); } // caller does not

StringBuilder s = new StringBuilder("hi");
mutate(s);   System.out.println(s); // hi!
reassign(s); System.out.println(s); // hi!  - unchanged
    Follow-ups they will ask

    How would you actually swap two values then?

    Return a new object/record holding both, pass a mutable holder (an array or a small container), or make the values fields of an object you mutate. There is no language-level way to rebind the caller's variable.

    Does this change for primitives?

    No — the mechanism is identical, it is just more obvious: the 4 bytes of the int are copied, so nothing the method does can be seen by the caller.

  • J03

    Integer arithmetic in Java wraps silently on overflow — no exception. Integer.MAX_VALUE + 1 is Integer.MIN_VALUE. The classic production bug is (low + high) / 2 in a binary search on a large array; write low + (high - low) / 2 instead. Use Math.addExact / multiplyExact when you want a failure instead of a wrong number.

    Floating point error is different: double is IEEE-754 binary, and 0.1 has no exact binary representation, exactly as 1/3 has no exact decimal one. So 0.1 + 0.2 == 0.30000000000000004. Never compare doubles with ==; compare with a tolerance, or avoid doubles entirely.

    For money, the rule is absolute: use BigDecimal or integer minor units (paise, cents). A fintech interviewer will notice immediately if you total currency in a double.

    Java
    int mid = (2_000_000_000 + 2_100_000_000) / 2; // negative! overflow
int safe = low + (high - low) / 2;              // correct

System.out.println(0.1 + 0.2 == 0.3);            // false
System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2"))); // 0.3

Math.addExact(Integer.MAX_VALUE, 1); // throws ArithmeticException
    Follow-ups they will ask

    Why is new BigDecimal(0.1) wrong?

    The double constructor captures the already-inaccurate binary value, giving 0.1000000000000000055511151231257827…. Always use new BigDecimal("0.1") or BigDecimal.valueOf(0.1).

    When is double acceptable?

    Measurements, physics, statistics, ML features — anywhere small relative error is fine and performance matters. Never for money, counts, or anything requiring exact equality.

  • J04

    var (Java 10+) is local-variable type inference, not dynamic typing. The compiler infers the static type from the initializer and it is fixed forever after. It works only for local variables with an initializer, for-loop variables, and try-with-resources — never for fields, method parameters, or return types.

    final means the binding cannot be reassigned. It says nothing about the object's contents: a final List can still have elements added. Effectively final means a variable is never reassigned even though it is not declared final — the compiler requires this for any local captured by a lambda or anonymous class.

    Scoping is block-based: a variable lives from declaration to the end of its enclosing block, and Java forbids shadowing a local with another local in a nested block (unlike fields, which locals may shadow).

    Java
    var list = new ArrayList<String>();  // inferred ArrayList<String>
// var x;            // illegal - no initializer
// var y = null;     // illegal - cannot infer

int count = 0;
Runnable r = () -> System.out.println(count); // ok while count is effectively final
// count++;   // adding this line breaks the lambda above
    Follow-ups they will ask

    Why does the lambda capture rule exist?

    Lambdas capture values, not variables — the value is copied into the lambda instance. Allowing reassignment would create two diverging copies with no defined semantics. Fields do not have this restriction because they are accessed through a reference.

    When is var bad style?

    When the initializer does not make the type obvious — var result = process(x) tells the reader nothing. It shines with long generic types: var m = new HashMap<String, List<Order>>().

  • J05

    The old switch statement falls through by default and works only on ints, enums and strings. The arrow form (case A -> …) removes fall-through entirely, and the switch expression returns a value, which lets the compiler enforce exhaustiveness.

    Exhaustiveness is the real win: over an enum or a sealed type, a switch expression with no default fails to compile if you add a new case and forget to handle it. That turns a runtime bug into a build error.

    Pattern matching for instanceof removes the cast-after-check ceremony, and record patterns go further by destructuring. Combined with sealed interfaces this is Java's answer to algebraic data types.

    Java
    // pattern matching for instanceof
if (o instanceof String s && s.length() > 3) { use(s); }

// switch expression, exhaustive over a sealed type
sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}

double area = switch (shape) {
    case Circle c  -> Math.PI * c.r() * c.r();
    case Square s  -> s.side() * s.side();
};  // no default needed - compiler proves it is exhaustive
    Follow-ups they will ask

    When would you still use the old colon form?

    When you genuinely want fall-through across several labels with shared logic, or when you need to yield from a complex block — though yield in the arrow form covers most of that now.

    What does exhaustiveness buy you architecturally?

    It makes adding a variant a compile-time task list: the build tells you every place that must change. That is a strong argument for sealed hierarchies over open ones in domain modelling.

  • J06

    Text blocks ("""…""", Java 15+) are multi-line string literals. The compiler strips incidental whitespace — the common indentation shared by all lines, determined by the least-indented line including the closing delimiter — so you can indent the block to match your code without polluting the value.

    They matter in real services for embedded SQL, JSON test fixtures, and HTML, where the alternative is unreadable concatenation with \n. Escapes still work, plus two new ones: \ at end of line suppresses the newline, and \s preserves a trailing space.

    Pair them with String.formatted() for interpolation — Java has no built-in string interpolation, so formatted is the idiomatic modern replacement for String.format.

    Java
    String sql = """
        SELECT id, amount
          FROM transactions
         WHERE account_id = ?
           AND created_at > ?
        """;

String msg = """
        Hello, %s.
        You have %d unread messages.
        """.formatted(name, count);
    Follow-ups they will ask

    How is incidental whitespace computed exactly?

    The minimum indentation across all non-blank lines and the closing delimiter line. Moving the closing """ left or right changes the stripping — a common surprise.

    Does a text block create a compile-time constant?

    Yes, if there are no escapes requiring runtime work — it is interned in the string pool just like a normal literal.

  • J07

    Arrays are covariant: String[] is a subtype of Object[]. That compiles, but the array carries its real component type at runtime, so storing the wrong type throws ArrayStoreException. Generics deliberately went the other way — they are invariant and erased — so this whole class of error is caught at compile time instead.

    Arrays are also reified: the JVM knows an int[] is an int array at runtime. Generics are erased, and that mismatch is why you cannot create new T[] and why mixing arrays with generics produces warnings.

    Multidimensional arrays in Java are arrays of arrays, not a contiguous rectangular block. Rows can have different lengths (jagged), and each row is a separate heap object — so a 2-D loop has worse cache locality than a flattened single array with index arithmetic.

    Java
    Object[] objs = new String[2];   // legal - covariance
objs[0] = 42;                    // ArrayStoreException at runtime

// List<Object> l = new ArrayList<String>(); // will not compile - invariant

int[][] grid = new int[3][];     // jagged is allowed
grid[0] = new int[5];
grid[1] = new int[2];
    Follow-ups they will ask

    Why did the language designers allow array covariance?

    Java 1.0 had no generics, so covariance was the only way to write a general-purpose sort(Object[]). Generics made it unnecessary, but it cannot be removed without breaking compatibility.

    How do you create a generic array safely?

    You do not, directly. Use (T[]) new Object[n] confined to a private field and never leak it as T[], or use Array.newInstance(clazz, n) when a Class<T> is available. This is exactly what ArrayList does internally.

  • J08

    Initialization runs in a strict order. Class level, once, on first active use: static fields and static blocks execute top to bottom. Instance level, on every construction: the superclass constructor runs first, then instance field initializers and instance blocks in source order, then the constructor body.

    That ordering causes a genuine trap: if a superclass constructor calls an overridable method, the subclass override runs before the subclass fields are initialized, so it sees nulls and zeros. The rule is never call an overridable method from a constructor.

    Static initialization is lazy and thread-safe — the JVM holds a class-init lock — which is the basis of the holder idiom for lazy singletons: no synchronization needed, and the instance is created on first access to the holder class.

    Java
    class Parent {
    Parent() { init(); }              // dangerous
    void init() {}
}
class Child extends Parent {
    private String name = "set";
    @Override void init() { System.out.println(name); } // prints null
}

// holder idiom - lazy, thread-safe, no locks
class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    static Config get() { return Holder.INSTANCE; }
}
    Follow-ups they will ask

    What counts as "first active use" of a class?

    Creating an instance, calling a static method, or reading a non-constant static field. Reading a static final compile-time constant does not trigger initialization — the value is inlined at compile time.

    What happens if a static initializer throws?

    The class is marked erroneous and every later use throws NoClassDefFoundError — often with the original ExceptionInInitializerError only in the first stack trace, which makes it a nasty production diagnosis.

  • J09

    Access modifiers run from most to least open: public, protected (subclasses plus same package), package-private (the default, same package only), and private. Package-private is underused and valuable — it lets you expose a class to its collaborators without making it part of your public API.

    JPMS (Java 9 modules) adds a layer above packages: a module-info.java declares which packages are exportsed and which modules it requires. Without an export, a public class is still inaccessible from outside the module — strong encapsulation that packages alone never gave you.

    In practice most Spring Boot services run on the classpath, not the module path, so JPMS rarely appears in application code. It matters for the JDK itself (which is why deep reflection into java.* internals now warns or fails) and for library authors.

    Java
    // module-info.java
module com.acme.payments {
    requires java.sql;
    requires transitive com.acme.core;   // consumers also get com.acme.core
    exports com.acme.payments.api;       // only this package is visible
    // com.acme.payments.internal stays hidden even though its classes are public
}
    Follow-ups they will ask

    What is the practical impact of JPMS on a Spring Boot app?

    Mostly the strong encapsulation of JDK internals: libraries doing setAccessible on java.* classes need --add-opens flags. Your own code usually stays on the classpath as an unnamed module.

    Why prefer package-private over public by default?

    Anything public is a contract you must keep. Package-private keeps refactoring cheap and makes the intended API surface obvious to the next reader.

  • J10

    A constructor initializes an object; it has no return type and its first statement is always a call to another constructor — either this(...) to chain within the class, or super(...) to the parent. If you write neither, the compiler inserts an implicit super(), which is why a parent with no no-arg constructor forces every child to call super explicitly.

    Telescoping constructors — a chain of overloads with growing parameter lists — are the classic smell once you pass three or four fields. The two fixes are a static factory with a meaningful name (Money.ofMinor(1250, INR)), or a builder when there are many optional fields.

    Validate in the constructor and throw, so an object can never exist in an invalid state. That is the single most valuable habit for domain classes: if it constructed, it is valid.

    Java
    final class Money {
    private final long minorUnits;
    private final Currency currency;

    private Money(long minorUnits, Currency currency) {
        if (currency == null) throw new IllegalArgumentException("currency required");
        this.minorUnits = minorUnits;
        this.currency = currency;
    }
    static Money ofMinor(long minor, Currency c) { return new Money(minor, c); }
    static Money zero(Currency c) { return new Money(0, c); }
}
    Follow-ups they will ask

    Why prefer a static factory over a public constructor?

    It can have a descriptive name, can return a cached or subtype instance, and can be made to fail before allocation. The cost is that the class cannot be subclassed if the constructor is private — often a feature.

    Can a constructor be private, and why would you?

    Yes — for singletons, static-factory-only classes, and utility classes that should never be instantiated. A private constructor in a utility class also stops the compiler generating a public default one.

  • J11

    Overriding replaces a superclass instance method; the call is resolved at runtime on the actual object type — that is dynamic dispatch, implemented via the vtable. Overloading is compile-time: the compiler picks among same-named methods by the static types of the arguments.

    Method hiding is the trap. Static methods are not polymorphic: redeclaring a static method in a subclass hides it, and which one runs depends on the reference type, not the object. The same applies to fields — fields are never polymorphic, they are always resolved by the declared type.

    Overriding rules: the signature must match, the return type may be covariant (narrower), access may widen but not narrow, and the override may throw fewer or narrower checked exceptions. Always annotate with @Override so a typo becomes a compile error instead of silent non-overriding.

    Java
    class A { static String who(){return "A";} String name(){return "A";} String f = "fA"; }
class B extends A { static String who(){return "B";} String name(){return "B";} String f = "fB"; }

A ref = new B();
System.out.println(ref.name()); // B  - overriding, dynamic dispatch
System.out.println(ref.f);      // fA - fields are not polymorphic
System.out.println(A.who());    // A  - statics are hidden, not overridden
    Follow-ups they will ask

    Why can an override not narrow visibility?

    Liskov substitution: code holding a supertype reference must be able to call the method. Narrowing would break that guarantee, so the compiler rejects it.

    How does the JVM make dynamic dispatch fast?

    A vtable lookup, and then the JIT often removes it entirely — if profiling shows a call site is monomorphic (only ever one type), it inlines the target and guards with a cheap type check.

  • J12

    Before Java 8 the rule was simple: abstract classes carry state and partial implementation, interfaces carry only a contract. Default methods blurred that — an interface can now ship behaviour — but the distinction that survives is state: interfaces still cannot have instance fields, and a class can implement many interfaces but extend only one class.

    So the modern decision rule is: use an interface for a capability that many unrelated types can have, and an abstract class only when subtypes genuinely share mutable state or construction logic. Default methods exist mainly for API evolution — adding stream() to Collection without breaking every implementation in the world.

    Interfaces can also have static methods (factories and helpers that belong to the type) and, since Java 9, private methods to share code between defaults without exposing it.

    Java
    interface Validator<T> {
    List<String> errors(T value);                       // abstract contract
    default boolean isValid(T value) {                  // added later, no breakage
        return errors(value).isEmpty();
    }
    static <T> Validator<T> alwaysValid() {             // static factory
        return v -> List.of();
    }
}
    Follow-ups they will ask

    Does a default method break the functional-interface property?

    No. A functional interface needs exactly one abstract method; any number of default and static methods is fine. That is how Comparator has thenComparing and still works as a lambda target.

    When is an abstract class clearly the right choice?

    Template Method — the parent fixes the algorithm's skeleton and holds shared state, subclasses fill in steps. AbstractList and Spring's JdbcTemplate family are the canonical examples.

  • J13

    Because a class can implement several interfaces, two of them may supply the same default method — a diamond. Java resolves it with three rules, in order: (1) class wins over interface — a concrete method inherited from a superclass beats any default; (2) the most specific interface wins — if one interface extends the other, the sub-interface's default is chosen; (3) otherwise it is a compile error, and the class must override the method explicitly.

    That third rule is the important one: Java refuses to guess. You resolve it by overriding and, if you want one of the inherited versions, calling it with the qualified Interface.super.method() syntax.

    This is why default methods did not reintroduce the C++ multiple-inheritance problem: state is still single-inheritance, and behaviour conflicts are a compile-time error rather than a silent choice.

    Java
    interface A { default String hello(){ return "A"; } }
interface B { default String hello(){ return "B"; } }

class C implements A, B {
    @Override public String hello() {
        return A.super.hello() + B.super.hello();   // explicit resolution
    }
}
    Follow-ups they will ask

    Why does "class wins" come first?

    Backward compatibility. Adding a default method to an interface must never change the behaviour of existing classes that already inherit a concrete implementation.

    Can you call A.super.hello() from anywhere?

    Only from a class that directly implements A, and only for a method A actually declares. You cannot reach a grandparent interface's default this way.

  • J14

    equals defines logical equality, and the contract has five clauses: reflexive (x.equals(x)), symmetric (x.equals(y) ⇔ y.equals(x)), transitive, consistent (repeated calls agree while nothing changes), and x.equals(null) is false.

    Symmetry and transitivity are what break in real code, almost always via inheritance: if a subclass adds a field and compares it, then sub.equals(super) is false while super.equals(sub) is true. There is no way to both extend a class with a new value field and preserve the contract — which is why value classes are usually final, and why getClass() comparison is safer than instanceof for them.

    Practical rules: compare the fields that define identity, use Objects.equals for nullable fields, and always override hashCode at the same time.

    Java
    @Override public boolean equals(Object o) {
    if (this == o) return true;                 // fast path
    if (o == null || getClass() != o.getClass()) return false;
    Account other = (Account) o;
    return Objects.equals(id, other.id);        // identity field only
}
@Override public int hashCode() { return Objects.hash(id); }
    Follow-ups they will ask

    getClass() or instanceof in equals?

    getClass() guarantees symmetry but breaks Liskov (a proxy or Hibernate subclass is never equal). instanceof plays well with proxies but requires the class to be final, or the added-field problem returns. For JPA entities, instanceof plus comparing only the business key is the usual compromise.

    Should equals use a mutable field?

    Almost never. If a field used by equals/hashCode changes after the object is put in a HashSet, the object becomes unreachable — it hashes to a different bucket than where it sits.

  • J15

    The contract is one sentence: equal objects must have equal hash codes. The converse is not required — unequal objects may collide, and must be allowed to.

    Break it by overriding equals without hashCode, and a HashMap stops working in a very specific way. put hashes the key to bucket A. Your later, equal lookup key hashes to bucket B (default hashCode is identity-based). The map searches bucket B, never finds the entry, and returns null — while the entry sits there permanently, invisible and unremovable.

    The second failure is mutating a key after insertion: the entry stays in the old bucket while the key now hashes elsewhere. It is a leak plus a lookup failure. This is why HashMap keys should be immutable — and why String, being immutable with a cached hash, is the ideal key.

    Java
    class Key { final int id; Key(int id){this.id=id;}
    @Override public boolean equals(Object o){ return o instanceof Key k && k.id==id; }
    // hashCode NOT overridden - broken
}
Map<Key,String> m = new HashMap<>();
m.put(new Key(1), "value");
System.out.println(m.get(new Key(1))); // null - equal but different bucket
    Follow-ups they will ask

    Does a good hashCode need to be unique?

    No — it needs to be well distributed. Collisions are handled by chaining (and treeing above 8 nodes in a bucket). A constant hashCode is technically legal and turns your map into a linked list: O(n) lookups.

    How does HashMap defend against poor hash functions?

    It spreads the bits with h ^ (h >>> 16) so high-order bits influence the low-order bucket index, and it converts a long collision chain into a red-black tree at 8 entries when capacity is at least 64.

  • J16

    Comparable.compareTo defines a total order: it must be antisymmetric, transitive, and consistent (if compareTo returns 0 for a pair, the sign must agree for all comparisons with a third element). The optional-but-strongly-recommended clause is consistency with equals: x.compareTo(y) == 0 should mean x.equals(y).

    When you break that, sorted collections misbehave in a way that looks like a bug in the JDK. TreeSet and TreeMap decide membership using compareTo, not equals — so a TreeSet ordered by, say, salary will silently reject a second employee earning the same amount as an existing one, treating them as duplicates.

    A non-transitive comparator is worse still: Arrays.sort's TimSort detects the inconsistency and throws IllegalArgumentException: Comparison method violates its general contract! — usually only on large inputs, so it passes tests and fails in production.

    Java
    record Emp(String name, int salary) {}
Set<Emp> set = new TreeSet<>(Comparator.comparingInt(Emp::salary));
set.add(new Emp("asha", 100));
set.add(new Emp("bela", 100));
System.out.println(set.size()); // 1 - bela was treated as a duplicate

// fix: make the comparator a total order with a tie-breaker
Comparator<Emp> c = Comparator.comparingInt(Emp::salary).thenComparing(Emp::name);
    Follow-ups they will ask

    Why does the JDK throw instead of just sorting wrongly?

    TimSort relies on the contract for correctness of its merge invariants; a violation can cause an ArrayIndexOutOfBounds deep inside the sort. The explicit check turns an incomprehensible crash into a diagnosable message.

    Which collections use compareTo vs equals?

    TreeSet/TreeMap and anything sorted use the comparator. HashSet/HashMap use equals/hashCode. So the same two objects can be duplicates in one and distinct in the other — a real source of confusion.

  • J17

    toString costs nothing to write and pays for itself in every log line and stack trace. Include the identifying fields; never include secrets — passwords, tokens, full card numbers — because toString ends up in logs you do not control.

    clone() is a broken design and worth being able to criticise: it is declared on Object but the Cloneable interface has no clone method (it is just a marker), the default implementation is a shallow field copy that bypasses constructors, and it interacts badly with final fields. Effective Java's advice is to avoid it.

    The replacements are a copy constructor (new ArrayList<>(other)) or a static copy factory (List.copyOf). They are ordinary code: they run constructors, work with final fields, can convert types, and let you choose shallow or deep explicitly.

    Java
    @Override public String toString() {
    return "Account[id=" + id + ", currency=" + currency + "]"; // no balance, no PAN
}

// copy constructor - explicit and deep where it matters
Account(Account other) {
    this.id = other.id;
    this.tags = new ArrayList<>(other.tags);   // defensive copy of mutable state
}
    Follow-ups they will ask

    What is the difference between shallow and deep copy here?

    Shallow copies references, so both objects share the same nested mutable state. Deep copies the nested objects too. A copy constructor makes the choice visible in the code; clone() hides it.

    Is there a legitimate use of clone?

    Copying arrays — arr.clone() is idiomatic, fast, and correct because arrays have no invariants to break.

  • J18

    An immutable class is built from five rules: make the class final (or the constructor private) so behaviour cannot be overridden; make every field private final; provide no setters or other mutators; defensively copy mutable inputs in the constructor; and defensively copy mutable state on the way out of getters.

    Missing either copy is the classic interview failure. Without the input copy, the caller keeps a reference to the list you stored and can mutate your object from outside. Without the output copy, the caller mutates the list you handed back — same result.

    Immutability buys thread safety for free: an object whose fields are all final is safely published by the JVM's final-field freeze semantics, so any thread that sees the reference is guaranteed to see fully initialized fields, with no synchronization.

    Java
    public final class Order {
    private final String id;
    private final List<Item> items;

    public Order(String id, List<Item> items) {
        this.id = id;
        this.items = List.copyOf(items);          // defensive copy IN

    Follow-ups they will ask

    Does final on a field make the object immutable?

    No — it stops reassignment of the reference only. private final List l can still have items added. Immutability is about the whole reachable object graph.

    What is safe publication and why does immutability give it?

    A correctly constructed object with only final fields cannot be seen half-initialized by another thread — the JMM inserts a freeze at the end of the constructor. Mutable objects need a happens-before edge (volatile write, lock, or a concurrent collection) to be published safely.

  • J19

    A record is a transparent carrier for data. The compiler generates a canonical constructor, accessor methods named after the components (id(), not getId()), and correct equals, hashCode and toString derived from all components. Records are implicitly final and cannot extend a class.

    What a record does not give you is deep immutability. record Order(String id, List<Item> items) holds a reference to the caller's list, which they can still mutate. Use a compact constructor to validate and copy.

    Use records for DTOs, API responses, value objects, and the carriers in a sealed hierarchy. Do not use them for JPA entities (which need a no-arg constructor and mutable identity) or for anything with meaningful behaviour beyond its data.

    Java
    record Order(String id, List<Item> items) {
    Order {                                   // compact constructor
        Objects.requireNonNull(id);
        items = List.copyOf(items);           // reassign before field assignment
    }
    // extra methods are allowed
    BigDecimal total() { return items.stream().map(Item::price)
            .reduce(BigDecimal.ZERO, BigDecimal::add); }
}
    Follow-ups they will ask

    Can a record have static fields or extra constructors?

    Static fields and methods yes; extra constructors yes, as long as they delegate to the canonical one. Instance fields beyond the components are forbidden — that is what keeps the record transparent.

    How do records interact with Jackson or JPA?

    Jackson supports records natively on recent versions. JPA does not — entities require a no-arg constructor and mutable fields, so keep records for the DTO layer and map to entities explicitly.

  • J20

    A sealed interface or class names exactly which types may implement or extend it, with a permits clause (implicit if the subtypes are in the same file). Every permitted subtype must itself be final, sealed, or explicitly non-sealed.

    The payoff is exhaustiveness. When the compiler knows the complete set of subtypes, a switch expression covering them all needs no default — and if someone adds a new subtype later, every such switch stops compiling until it is handled. You get a build-time checklist instead of a runtime surprise.

    Sealed types plus records plus pattern matching is the modern way to model a closed domain — payment methods, order states, parse results. Prefer it over an enum when each variant carries different data, and over an open hierarchy when the set of variants is genuinely fixed.

    Java
    sealed interface PaymentResult permits Approved, Declined, Pending {}
record Approved(String authCode) implements PaymentResult {}
record Declined(String reason, boolean retryable) implements PaymentResult {}
record Pending(Instant checkAfter) implements PaymentResult {}

String describe(PaymentResult r) {
    return switch (r) {
        case Approved a -> "ok " + a.authCode();
        case Declined d when d.retryable() -> "retry: " + d.reason();
        case Declined d -> "final decline: " + d.reason();
        case Pending p  -> "check after " + p.checkAfter();
    };  // exhaustive - adding a 4th variant breaks the build here
}
    Follow-ups they will ask

    Sealed interface or enum — how do you choose?

    Enum when the variants are constants with the same shape. Sealed when each variant carries different data. An enum cannot give Approved an authCode and Declined a reason; a sealed hierarchy can.

    What does non-sealed mean?

    It deliberately reopens one branch for extension — useful when you want a fixed core set plus one genuinely extensible variant. It also means switches over that hierarchy again need a default.

  • J21

    An enum is a fixed set of instances created by the JVM at class-initialization time. Because that initialization is lazy and guarded by the class-init lock, enums are the correct singleton: thread-safe, lazily created, and — crucially — immune to the two attacks that break other singletons, since serialization is handled specially and reflection cannot construct enum instances.

    Enums can carry state and behaviour. Give them fields with a constructor, and even per-constant behaviour with an abstract method implemented by each constant — that is Strategy pattern with no boilerplate and compile-time exhaustiveness.

    For collections of enums use EnumMap and EnumSet, not HashMap/HashSet. They are backed by an array and a bitmask respectively — dramatically faster and smaller, with iteration in declaration order.

    Java
    enum Operation {
    PLUS("+") { public long apply(long a, long b){ return a + b; } },
    TIMES("*") { public long apply(long a, long b){ return a * b; } };

    private final String symbol;
    Operation(String symbol){ this.symbol = symbol; }
    public abstract long apply(long a, long b);
}

enum Singleton { INSTANCE; public void work(){} }   // safest singleton in Java

    Follow-ups they will ask

    Why is the enum singleton safer than the holder idiom?

    Both are lazy and thread-safe, but only the enum is automatically safe against reflection (the JVM forbids reflective enum construction) and against serialization creating a second instance.

    What is wrong with persisting enum.ordinal()?

    Ordinal is positional — inserting a constant in the middle silently remaps every stored value. Persist the name() or an explicit stable code field instead.

  • J22

    Four flavours. A static nested class is just a top-level class scoped inside another — no link to an outer instance. An inner (non-static nested) class holds an implicit reference to its enclosing instance, so it can use the outer object's fields. An anonymous class is a one-off subclass or implementation declared inline. A local class is named but declared inside a method.

    The leak follows directly from that implicit reference: if an inner class instance outlives its outer object — stored in a static registry, handed to a long-lived listener, submitted to an executor — the whole outer object stays reachable and can never be collected. The same applies to anonymous classes and to non-static Runnables in Android/Swing code.

    The fix is almost always static: make the nested class static and pass what it needs explicitly. Lambdas do not capture this unless you reference an instance member, which is one reason they leak less than anonymous classes.

    Java
    class Service {
    private byte[] bigCache = new byte[10_000_000];

    class Task implements Runnable {           // inner - holds Service.this
        public void run() { /* ... */ }
    }
    static class SafeTask implements Runnable { // static - holds nothing
        public void run() { /* ... */ }
    }
}
// registry.add(service.new Task()); // pins the 10MB cache forever
    Follow-ups they will ask

    How do you see this in a heap dump?

    The inner class instance shows a synthetic field named this$0 pointing at the outer instance. Following the dominator tree from the leaked object leads straight to the outer object's retained size.

    Do lambdas capture the enclosing instance?

    Only if they reference an instance field or method. A lambda that touches only its parameters and effectively-final locals is compiled to a static method and captures nothing.

  • J23

    Inheritance couples you to a superclass you do not control: its internal call patterns become part of your contract. The canonical example is extending HashSet to count additions — addAll internally calls add, so your counter double-counts, and a future JDK version could change that and silently break you. That is the fragile base class problem.

    Composition with delegation avoids it: hold the collaborator as a field, implement the interface, forward the calls you want and add your behaviour around them. You depend on the published interface, not on the implementation's internal choices. This is the Decorator pattern.

    Liskov substitution is the test for when inheritance is right: a subtype must be usable anywhere the supertype is, without surprising the caller. Square extends Rectangle fails it — code that sets width and height independently and asserts the area breaks, because a square cannot honour that contract. The relationship is not "is-a" in the behavioural sense.

    Java
    // composition + delegation instead of extending HashSet
class CountingSet<E> implements Set<E> {
    private final Set<E> delegate;
    private int addCount;
    CountingSet(Set<E> delegate){ this.delegate = delegate; }

    @Override public boolean add(E e){ addCount++; return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c){
        addCount += c.size(); return delegate.addAll(c);   // no double count
    }
    // remaining methods forward to delegate
}
    Follow-ups they will ask

    When is inheritance still the right tool?

    Within a codebase you own, for a genuine is-a relationship with a stable contract — typically Template Method, where the parent defines the algorithm and documents exactly which methods subclasses may override. Effective Java's rule: design and document for inheritance, or prohibit it with final.

    How does this show up in a code review?

    Someone extends a framework class to add a field or hook. Ask what happens when the framework changes its internal call sequence — if the answer is "we break silently", it should be composition.

    String is immutable: the backing array is final and never handed out, and the hash is cached after first computation. That gives thread safety with no synchronization, safe use as a HashMap key, and safe sharing across security boundaries (a checked filename cannot be changed afterwards).

    The string pool is a JVM-managed table of unique string instances. String literals are automatically interned at class load, so two identical literals are the same object — which is why == deceptively works for literals but fails for runtime-built strings. intern() puts a runtime string into the pool and returns the canonical instance. Since Java 7 the pool lives in the heap (not PermGen), so interning heavily is a GC concern, not a PermGen-overflow one.

    Compact strings (Java 9+) store Latin-1 text in a byte[] with a coder flag instead of always using char[], roughly halving memory for typical ASCII-heavy applications — one of the largest free wins in modern JDKs.

    Java
    String a = "hello";
String b = "hello";
String c = new String("hello");
System.out.println(a == b);            // true  - same pooled literal
System.out.println(a == c);            // false - new object on the heap
System.out.println(a == c.intern());   // true  - canonical instance
System.out.println(a.equals(c));       // true  - always compare this way
    Follow-ups they will ask

    Why is immutability what makes String a good HashMap key?

    The hash cannot change after insertion, so the entry stays findable in its bucket, and the cached hash makes repeated lookups cheap. A mutable key breaks both.

    When would you deliberately call intern()?

    Rarely — when parsing huge inputs with massive duplication (log tags, column names) and you want one instance each. Measure first: the pool is a hash table with its own cost, and a plain HashMap-based canonicalizer is often better.

  • J25

    String concatenation in a loop is O(n²): each s += x allocates a new string and copies everything so far. Over 10,000 iterations that is tens of millions of copied characters. Use a StringBuilder, which keeps a growable buffer and appends in amortized O(1).

    StringBuilder and StringBuffer have identical APIs; the difference is that StringBuffer's methods are synchronized. That synchronization is almost never useful — a builder is nearly always confined to one method — so StringBuilder is the default and StringBuffer is legacy.

    Note that the compiler already converts simple a + b + c in a single expression into an efficient concatenation (since Java 9, via invokedynamic and StringConcatFactory). It cannot do that across loop iterations, which is exactly why the loop case is the one that hurts.

    Java
    // O(n^2) - allocates and copies on every iteration
String s = "";
for (String part : parts) s += part;

// O(n) - one growable buffer
StringBuilder sb = new StringBuilder(parts.size() * 16); // pre-size if known
for (String part : parts) sb.append(part);
String result = sb.toString();

// idiomatic alternative
String joined = String.join(", ", parts);
    Follow-ups they will ask

    Does pre-sizing the StringBuilder matter?

    Yes for large outputs — the default capacity is 16 and growth copies the whole buffer. If you can estimate the size, one allocation replaces a dozen array copies.

    Is a + b inside a method ever a problem?

    No. A single expression compiles to one efficient concatenation. Only repeated concatenation across statements or iterations is quadratic.

    Two roots: Collection (List, Set, Queue/Deque) and Map, which is deliberately not a Collection because its elements are pairs. List is ordered with duplicates and index access. Set is unique membership. Queue/Deque is insertion-order processing from the ends. Map is key→value lookup.

    Choose by access pattern, not habit. Random access by index → ArrayList. Membership tests → HashSet. Key lookup → HashMap. Ordered iteration → LinkedHashMap/TreeMap. FIFO or LIFO → ArrayDeque. Priority ordering → PriorityQueue. Sorted range queries → TreeMap's headMap/tailMap/floorKey.

    Know the three implementation families for the hashed types: Hash* (unordered, O(1)), Linked* (insertion or access order, O(1) plus a linked list), Tree* (sorted, O(log n)). Saying which family you want and why is a fast way to sound fluent.

    Java
    List<String>   byIndex   = new ArrayList<>();    // O(1) get, O(n) middle insert
Set<String>    unique    = new HashSet<>();      // O(1) contains, no order
Set<String>    inOrder   = new LinkedHashSet<>();// O(1) contains, insertion order
NavigableMap<Integer,String> sorted = new TreeMap<>(); // O(log n), range queries
Deque<Task>    stackOrQ  = new ArrayDeque<>();   // both stack and queue, fast
Queue<Job>     byPriority= new PriorityQueue<>(Comparator.comparingInt(Job::cost));

    Why is Map not a Collection?

    A Collection holds single elements; a Map holds mappings. Making Map a Collection would force an element type that is neither key nor value. Instead Map exposes three collection views: keySet, values, entrySet — and those views are live, so removing from keySet removes from the map.

    Which one for a stack?

    ArrayDeque. The legacy Stack extends Vector, is synchronized, and iterates in the wrong order (bottom-up). Deque's push/pop/peek is the modern answer.

  • J27

    ArrayList wraps an Object[]. Size is how many elements you have; capacity is how long the array is. When size reaches capacity, it grows by roughly 50% (newCap = old + (old >> 1)), allocates a new array, and copies via System.arraycopy — an intrinsic that the JIT turns into a fast bulk memory move.

    So add at the end is amortized O(1), get is O(1), but add/remove in the middle is O(n) because everything after shifts. Removing from the front of a large list in a loop is the classic accidental O(n²).

    Pre-size when you know the count (new ArrayList<>(expected)) to avoid repeated grow-and-copy. And know trimToSize() exists for long-lived lists that shrank.

    Java
    List<String> l = new ArrayList<>(10_000);   // one allocation instead of ~20 grows

// O(n^2) - each remove shifts the tail
for (int i = 0; i < list.size(); i++) if (bad(list.get(i))) list.remove(i--);

// O(n) - single pass, uses the iterator internally
list.removeIf(this::bad);

    Why 1.5x growth rather than 2x?

    It trades a little more copying for less wasted memory, and the freed blocks are more likely to be reusable for the next allocation. It is a heuristic, not a rule — other languages pick 2x.

    What does subList return?

    A view, not a copy — writes through to the backing list, and structural modification of the parent invalidates it with ConcurrentModificationException. Useful for range operations, dangerous if you store it.

  • J28

    On paper LinkedList wins for insertion and deletion (O(1) at a known node) and loses for indexed access (O(n)). In practice it loses almost everywhere, because Big-O ignores cache locality. ArrayList's elements sit in one contiguous array, so the CPU prefetcher streams through them; LinkedList's nodes are scattered across the heap, so nearly every step is a cache miss — and each node also costs an extra ~24 bytes of object header and two pointers.

    Also note the hidden cost: to insert "in the middle" of a LinkedList you must first walk to that position, which is O(n) anyway. The O(1) benefit only materializes when you already hold an iterator at the spot.

    For queue and stack use cases the right answer is ArrayDeque: a circular array, no per-element node objects, and faster than both LinkedList and the legacy Stack. The honest interview answer is "LinkedList is almost never the right choice; I would use ArrayList or ArrayDeque."

    Java
    Deque<Task> stack = new ArrayDeque<>();
stack.push(t);      // addFirst
stack.pop();        // removeFirst

Deque<Task> queue = new ArrayDeque<>();
queue.offer(t);     // addLast
queue.poll();       // removeFirst
// ArrayDeque forbids null elements - poll() returning null unambiguously means empty
    Follow-ups they will ask

    Is there any case where LinkedList genuinely wins?

    When you hold an iterator and repeatedly insert/remove at that position in a very large list, or when you need a Deque that permits null elements. Both are rare.

    Why does ArrayDeque forbid nulls?

    Because null is its sentinel for "empty" in poll and peek. Allowing null elements would make those return values ambiguous.

  • J29

    A HashMap is an array of buckets. For a key it computes h = key.hashCode(), spreads it with h ^ (h >>> 16) so high bits influence the result, then indexes with h & (capacity - 1) — which works because capacity is always a power of two.

    Collisions chain in a linked list. Since Java 8, once a single bucket reaches 8 nodes and the table has at least 64 buckets, that chain converts to a red-black tree, changing worst-case lookup from O(n) to O(log n) — a defence against hash-collision denial-of-service. It converts back at 6 nodes; the gap between 8 and 6 is hysteresis so a map hovering at the boundary does not thrash.

    Resize happens when size exceeds capacity × load factor (0.75 by default, a measured balance between space and collision rate). Capacity doubles, and because it doubles, each old bucket's entries split into just two destinations — the same index, or that index plus the old capacity — decided by one extra bit. Java 8 preserves relative order during the split, which fixed the infinite-loop race that Java 7's reversal could cause under concurrent resize.

    Java
    // why capacity is a power of two:  h & (cap-1) == h % cap, but far cheaper
int index = (n - 1) & hash;

// pre-size to avoid resizes: capacity must exceed expected/0.75
Map<String,Order> m = new HashMap<>((int)(expected / 0.75f) + 1);
    Follow-ups they will ask

    Why is HashMap unsafe under concurrency even for reads during a write?

    A concurrent resize can leave a thread traversing a half-migrated table, producing lost entries or (in Java 7) a cyclic chain that spins forever at 100% CPU. Use ConcurrentHashMap.

    What makes a good key class?

    Immutable, with equals and hashCode over the same identity fields, and a well-distributed hash. String, Integer, enum and records are all good. A mutable entity with a generated id that changes on persist is a bad key.

    LinkedHashMap is a HashMap plus a doubly linked list threaded through the entries, so iteration has a predictable order at a small memory cost. The third constructor argument chooses the order: false = insertion order (default), true = access order, where every get or put moves the entry to the end.

    Access order plus one overridden method gives you an LRU cache in about five lines. removeEldestEntry is called after each insertion; return true to evict the head, which under access order is the least recently used entry.

    Be explicit about the limits in an interview: this is not thread-safe (wrap with Collections.synchronizedMap or use Caffeine), and it has no TTL. For production caching, name Caffeine or Redis — but be able to write this by hand, because it is a standard exercise.

    Java
    class LruCache<K,V> extends LinkedHashMap<K,V> {
    private final int max;
    LruCache(int max) {
        super(16, 0.75f, true);          // true = access order
        this.max = max;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > max;
    }
}
    Follow-ups they will ask

    How would you write the same thing without LinkedHashMap?

    A HashMap from key to node, plus a doubly linked list with sentinel head and tail nodes. get looks up the node and moves it to the tail; put inserts at the tail and evicts from the head when over capacity. Sentinels remove all the null-checking.

    How do you make it thread-safe without a global lock?

    In practice you do not hand-roll it — you use Caffeine, which uses ring buffers to record accesses and applies them asynchronously, so reads do not contend. Explaining why a naive synchronized LRU serializes all reads is the point.

  • J31

    TreeMap is a red-black tree: a self-balancing binary search tree where every operation — get, put, remove — is O(log n) and iteration is in sorted key order. TreeSet is a TreeMap with dummy values.

    The real reason to pick it over a HashMap is the NavigableMap API: floorKey, ceilingKey, higherKey, headMap, tailMap, subMap, firstEntry, pollFirstEntry. Range and nearest-neighbour queries are exactly what a hash map cannot do.

    Two gotchas. Ordering comes from compareTo or the supplied Comparator, not from equals — so an inconsistent comparator silently merges distinct elements. And TreeMap rejects null keys, because it must compare them.

    Java
    NavigableMap<Instant, Rate> rates = new TreeMap<>();
rates.put(t1, r1); rates.put(t2, r2);

Rate atOrBefore = rates.floorEntry(when).getValue();     // "rate in effect at `when`"
Map<Instant,Rate> window = rates.subMap(from, true, to, false);
Map.Entry<Instant,Rate> latest = rates.lastEntry();
    Follow-ups they will ask

    When is TreeMap the right choice over sorting a list?

    When the data changes and you need to keep querying — a list must be re-sorted on every change (O(n log n)) while a TreeMap absorbs each change in O(log n). For a static dataset, a sorted array with binary search is faster and more compact.

    What is a red-black tree's guarantee?

    No path from root to leaf is more than twice as long as any other, which bounds height at O(log n). It rebalances with rotations and recolouring on insert and delete.

    PriorityQueue is a binary min-heap stored in an array: the smallest element by the comparator is always at index 0. offer and poll are O(log n) (sift up / sift down), peek is O(1), and building from a collection is O(n) via heapify.

    The classic surprise: iteration and toString are not sorted. The heap only guarantees the parent-child invariant, not a total order in the array. The only sorted access is repeatedly polling.

    It is the workhorse for top-K problems. For "K largest", keep a min-heap of size K and poll whenever it exceeds K — O(n log K) time and O(K) space, which beats sorting the whole input when K is small. It is also the core of Dijkstra, task scheduling, and merge-K-sorted-lists.

    Java
    // K largest with a size-K MIN heap
PriorityQueue<Integer> heap = new PriorityQueue<>();     // natural = min-heap
for (int x : nums) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();                    // drop the smallest
}
// heap now holds the k largest; heap.peek() is the kth largest

PriorityQueue<Job> maxByCost = new PriorityQueue<>(Comparator.comparingInt(Job::cost).reversed());
    Follow-ups they will ask

    Is PriorityQueue stable for equal priorities?

    No — ties break arbitrarily. If you need FIFO among equal priorities, add a monotonically increasing sequence number as a tie-breaker in the comparator.

    How would you support removing an arbitrary element efficiently?

    remove(Object) is O(n) because it must scan. For efficient decrease-key or removal (as Dijkstra sometimes wants), keep a map from element to its heap index and sift from there, or use the lazy-deletion trick of marking entries stale and skipping them on poll.

    An Iterator gives sequential access plus a safe remove. ListIterator adds bidirectional traversal, set, and add. Both exist so you can modify while traversing without corrupting the structure.

    Fail-fast iterators (ArrayList, HashMap, most of java.util) track a modCount on the collection. The iterator snapshots it and compares on every next(); if the collection was structurally modified by anything other than the iterator itself, it throws ConcurrentModificationException. This is a best-effort bug detector, not a guarantee — never write code that depends on catching it.

    Fail-safe (weakly consistent) iterators — ConcurrentHashMap, CopyOnWriteArrayList — never throw. They either iterate a snapshot (COW) or reflect some state between creation and traversal (CHM). The tradeoff is that you may not see very recent writes.

    Java
    // ConcurrentModificationException
for (String s : list) if (s.isBlank()) list.remove(s);   // boom

// correct: remove through the iterator
Iterator<String> it = list.iterator();
while (it.hasNext()) if (it.next().isBlank()) it.remove();

// clearest
list.removeIf(String::isBlank);
    Follow-ups they will ask

    Why is fail-fast only best-effort?

    modCount is not volatile and the check is unsynchronized, so under real concurrency a modification may go unseen. It reliably catches the single-threaded mistake, which is what it is for.

    What does "weakly consistent" guarantee exactly?

    That the iterator will not throw, will traverse elements as they existed at some point at or after creation, and will not return an element twice. It may or may not reflect concurrent updates.

    Since Java 8, comparators compose declaratively instead of being hand-written. Comparator.comparing(Order::getAmount) builds one from a key extractor; thenComparing chains tie-breakers; reversed() flips the whole chain built so far.

    Use the primitive-specialized forms — comparingInt, comparingLong, comparingDouble — when the key is a primitive, to avoid boxing on every comparison inside the sort.

    Java
    Comparator<Employee> byDeptThenSalaryDesc =

    Comparable is the type's own natural order, implemented on the class itself (compareTo). Comparator is an external, swappable ordering — you can have many, and they can order types you do not own.

    Why does comparing(...).reversed() often surprise people?

    reversed() reverses the entire composed comparator to its left, including tie-breakers. If you only want the first key reversed, reverse that key's comparator inside comparing, as in the example above.

    Collections and Arrays are the static utility toolboxes: Collections.sort/reverse/shuffle/frequency/disjoint/nCopies/emptyList, and Arrays.sort/fill/copyOf/asList/stream/equals/deepToString. Knowing they exist saves you writing loops in an interview.

    Is List.of() the same as Collections.emptyList()?

    Both are immutable and empty. List.of() returns a shared instance too, but disallows nulls throughout the of family — the deliberate design choice that nulls are not valid elements.

    Optional exists to make "there might be no result" explicit in a method signature, so callers cannot forget. Its intended and only strong use is as a return type.

    The anti-patterns are worth naming because interviewers probe them: do not use Optional for fields (it is not Serializable and adds an object per instance), not for method parameters (use an overload), not as a collection element (an empty collection already means "nothing"), and never call get() without isPresent() — use orElse, orElseGet, orElseThrow, or map.

    Know the difference between orElse and orElseGet: orElse(expensive()) evaluates the argument always, even when a value is present. orElseGet(() -> expensive()) only on absence. This is a real performance bug in production code.

    The java.time rule of thumb: Instant is a point on the global timeline (UTC, machine time). LocalDateTime is a wall-clock reading with no zone — it is not an instant and cannot be converted to one without a zone. ZonedDateTime is a local time plus a zone id, which handles DST rules. OffsetDateTime is local time plus a fixed offset, with no DST rules.

A future meeting → LocalDateTime plus the zone id (not the offset), because governments change DST rules and the meeting should stay at 9am local. A birthday → LocalDate. A duration between instants → Duration; a calendar amount like "one month" → Period.

    BigDecimal is arbitrary-precision decimal arithmetic: an unscaled BigInteger plus a scale (digits after the decimal point). Because it is decimal, 0.1 is exactly 0.1 — which is the whole reason it exists for money.

    Three rules. Never use the double constructor — new BigDecimal(0.1) captures the already-wrong binary value; use new BigDecimal("0.1") or BigDecimal.valueOf(0.1). Always specify scale and RoundingMode on divide, or a non-terminating result throws ArithmeticException. And compare with compareTo, not equals — equals also compares scale, so 2.0 does not equal 2.00.

    The alternative many payment systems use is integer minor units: store paise or cents in a long. It is exact, fast, and impossible to misround — at the cost of tracking the currency's exponent yourself.

    Java

    Which RoundingMode for money?

    HALF_UP or HALF_EVEN (banker's rounding). HALF_EVEN reduces cumulative bias across many roundings, which is why financial standards often mandate it. The important thing is that it is a stated business decision, not a default.

    How do you split 100.00 three ways without losing a paisa?

    Round down for each share, then distribute the remainder one minor unit at a time. Never round each share independently and hope the total matches — reconciliation will catch it.

    Java regex compiles a Pattern (expensive) into a matcher (cheap). Compile once into a static final Pattern and reuse it — recompiling inside a loop or a request handler is a common, invisible performance drain. Note Pattern is thread-safe; Matcher is not.

    Catastrophic backtracking is the security-relevant part. Java's engine is backtracking, so nested quantifiers over overlapping character classes — (a+)+b, (\d+)*$ — can take exponential time on a non-matching input. A 30-character crafted string can hang a thread; if that regex sits in a request path, it is a denial-of-service (ReDoS).

    Mitigations: avoid nested quantifiers, use possessive quantifiers (a++) or atomic groups ((?>…)) which forbid backtracking, anchor your patterns, and cap input length before matching. For simple work prefer String.split, startsWith, or indexOf — they are clearer and immune.

    Java
    private static final Pattern EMAIL =
        Pattern.compile("^[\\w.+-]+@[\\w-]+\\.[\\w.]+$");   // compiled once

boolean ok = EMAIL.matcher(input).matches();

// vulnerable: nested quantifier, exponential on "aaaaaaaaaaaaaaaaaaaaaaaaX"
Pattern bad = Pattern.compile("(a+)+b");
// safer: possessive quantifier forbids backtracking
Pattern good = Pattern.compile("(a++)+b");
    Follow-ups they will ask

    How would you find a ReDoS risk in a code review?

    Look for nested quantifiers or alternations where the branches can match the same characters, applied to user-controlled input. Then test with a long string of the repeated character followed by one that forces failure.

    Matcher reuse?

    A Matcher is stateful and not thread-safe — create one per use (pattern.matcher(input)), or call reset(). Only the Pattern should be shared.

    A String in memory is Unicode; bytes on disk or the wire are an encoding of it. That is how the same code produces correct output locally and mojibake in production.

    So the rule is absolute: always pass an explicit charset, and make it StandardCharsets.UTF_8 unless something forces otherwise. Java 18 changed the default file encoding to UTF-8 (JEP 400), which helps, but explicit is still correct and portable across versions.

    Two deeper points for depth: String.length() returns UTF-16 code units, so an emoji or many CJK characters count as 2 — use codePointCount when you mean characters. And a multi-byte character can straddle a buffer boundary, so decoding must be done by a Reader, never by decoding fixed-size byte chunks independently.

    Java

    Characters are 1–4 bytes. Truncating a UTF-8 byte array to fit a database column can cut a character in half and produce invalid output — truncate by code points, or let the database enforce it.

    Generics give compile-time type safety and remove casts. Before them, List held Objects and every read needed a cast that could fail at runtime; List<String> moves that failure to compile time.

    A bounded type parameter constrains what T can be, which is what lets you call methods on it: <T extends Comparable<T>> means T must be comparable to itself, so you may call compareTo inside. Bounds can be multiple: <T extends Number & Serializable> (class first, then interfaces).

    Generic methods declare their own parameter before the return type and are usually preferable to generifying the whole class when only one method needs it — the type is then inferred per call.

    Java
    // generic method with a bound - can call compareTo because of the bound
static <T extends Comparable<T>> T max(List<T> list) {
    T best = list.get(0);
    for (T t : list) if (t.compareTo(best) > 0) best = t;
    return best;
}

// multiple bounds
static <T extends Number & Comparable<T>> void check(T t) {}
    Follow-ups they will ask

    Why <T extends Comparable<T>> rather than just Comparable?

    The raw form loses the type and forces a cast. The parameterized bound says T is comparable to its own type, which is what makes the comparison type-safe.

    Generic class or generic method?

    Method, when only that operation is generic — it keeps the class simple and infers types at each call site. Class, when the type parameter is part of the object's identity (a Repository<Order>).

    Generics are implemented by erasure: the compiler checks types, then erases them, replacing T with its bound (Object if unbounded) and inserting casts. At runtime List<String> and List<Integer> are the same class. This was a compatibility decision — generic and pre-generic code had to interoperate on the same JVM.

    The consequences are the interview material: you cannot write new T() or new T[n], you cannot do x instanceof List<String>, you cannot overload on List<String> vs List<Integer> (same erasure), and static fields are shared across all parameterizations.

    Bridge methods are the compiler's patch for erasure plus covariant overriding: when a generic superclass method erases to compareTo(Object) but your subclass declares compareTo(Person), the compiler synthesizes a bridge compareTo(Object) that casts and delegates, so polymorphism still works.

    Java

// T instance = new T();
// T[] arr = new T[10];
// if (list instanceof List<String>) {}
// void f(List<String> l) {} void f(List<Integer> l) {}  // same erasure

// the standard workaround: pass the Class token
static <T> T create(Class<T> type) throws Exception {
    return type.getDeclaredConstructor().newInstance();
}
    Follow-ups they will ask

    How do libraries like Jackson get around erasure?

    With a super type token: an anonymous subclass captures the type argument in its class file (new TypeReference<List<Order>>(){}), and reflection reads it from the generic superclass signature. Generic type information does survive in class metadata — it is only absent from instances.

    What is heap pollution in one sentence?

    A variable of a parameterized type referring to an object that is not of that parameterized type — possible because erasure removes the runtime check, and the failure surfaces later as an unexpected ClassCastException.

  • J44

    Generics are invariant: List<String> is not a List<Object>, even though String is an Object. That is what stops the ArrayStoreException problem arrays have. Wildcards restore the flexibility safely.

    ? extends T is a producer: you can read T out of it, but cannot write anything in (except null), because the compiler does not know the exact subtype. ? super T is a consumer: you can write T into it, but reads come back as Object.

    That is PECS — Producer Extends, Consumer Super. Apply it to any method that only reads from or only writes to a parameter, and your API becomes usable with subtypes and supertypes. Use an unbounded ? when you genuinely do not care about the type (e.g. List<?> l; l.size()).

    Java
    // src produces T (read only), dst consumes T (write only)
static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T t : src) dst.add(t);
}

List<Integer> ints = List.of(1,2,3);
List<Number>  nums = new ArrayList<>();
copy(ints, nums);         // works only because of the wildcards

List<? extends Number> producer = ints;
// producer.add(4);       // illegal - could be a List<Double>
Number n = producer.get(0);  // fine
    Follow-ups they will ask

    Should wildcards appear in return types?

    No. A wildcard in a return type forces every caller to deal with the wildcard, and it propagates through their code. Accept wildcards in parameters, return concrete parameterized types.

    Why can you always add null to a ? extends T?

    Because null is assignable to every reference type, so it is safe regardless of what the actual type argument turns out to be.

    Heap pollution is when a variable of parameterized type points at an object of a different parameterization — erasure makes it possible, and the ClassCastException appears somewhere far from the cause. Varargs are the main gateway, because T... args creates a T[], and generic arrays are exactly what the language cannot make safe.

    That is why any method with a generic varargs parameter produces an unchecked warning. @SafeVarargs suppresses it and is a promise you are making: the method only reads from the varargs array and never stores it anywhere or exposes it. It is allowed only on static, final, or private methods — ones that cannot be overridden and made unsafe.

    Never blanket-suppress unchecked warnings. Suppress at the narrowest scope with a comment explaining why the cast is provably safe; a codebase with warnings switched off everywhere has lost the type system's help.

    Java
    @SafeVarargs                      // I promise not to store or leak the array

    return new ArrayList<>(Arrays.asList(items));   // read only
}

    Why is @SafeVarargs restricted to static/final/private methods?

    An overridable method could be replaced by an unsafe implementation in a subclass, invalidating the promise made by the annotation on the parent.

    What is the safest generic-varargs API shape?

    Take a Collection<T> instead of T... when you can. It sidesteps the array entirely.

    A recursive generic bound is a type parameter constrained in terms of itself: <T extends Comparable<T>>. It expresses "comparable to its own type" — which is what makes max(List<T>) type-safe without casts. It looks strange the first time and is a good signal of comfort with generics.

    The same trick solves the fluent builder inheritance problem. A plain builder's withX() returns the parent builder type, so once you call a parent method you can no longer chain subclass methods. Declaring Builder<T extends Builder<T>> with an abstract self() lets each method return T — the concrete subclass type — so chaining works in any order.

    This is sometimes called the curiously recurring generic pattern. Use it when you genuinely have a builder hierarchy; for a single builder, plain methods returning the builder are simpler and better.

    Java
    abstract class Builder<T extends Builder<T>> {
    protected String name;
    public T name(String n){ this.name = n; return self(); }
    protected abstract T self();
}
class UserBuilder extends Builder<UserBuilder> {
    private String email;
    public UserBuilder email(String e){ this.email = e; return this; }
    @Override protected UserBuilder self(){ return this; }
}

new UserBuilder().name("asha").email("a@b.c");   // chains in any order
    Follow-ups they will ask

    What breaks without the self-type?

    name() returns Builder, so .name(...).email(...) fails to compile — you would have to call subclass methods first, which is a fragile API.

    Is there a simpler alternative?

    Yes — favour composition or a single non-inherited builder, or use a record plus a with-style copy method. The self-type is worth it only when the hierarchy is real.

    A functional interface has exactly one abstract method, so a lambda can implement it. @FunctionalInterface is optional but makes the intent explicit and fails the build if someone adds a second abstract method.

    The core set in java.util.function: Function<T,R> (apply), Supplier<T> (get, no input), Consumer<T> (accept, no output), Predicate<T> (test → boolean), BiFunction/BiConsumer/BiPredicate for two arguments, UnaryOperator<T> and BinaryOperator<T> for same-type shorthand.

    The primitive specializations matter for performance: IntPredicate, ToIntFunction, IntUnaryOperator, IntSupplier. They exist to avoid boxing every value in a hot pipeline. Also know the default methods that compose them: andThen, compose, and, or, negate.

    Java
    Function<Order, BigDecimal> amount = Order::total;
Predicate<Order> large = o -> o.total().compareTo(THRESHOLD) > 0;
Predicate<Order> recent = o -> o.created().isAfter(cutoff);

List<Order> flagged = orders.stream()
        .filter(large.and(recent.negate()))     // composition
        .toList();

ToIntFunction<Order> itemCount = o -> o.items().size();  // no boxing
    Follow-ups they will ask

    Difference between andThen and compose?

    f.andThen(g) runs f first then g; f.compose(g) runs g first then f. Same operations, opposite order — name it correctly and you look precise.

    Can a functional interface extend another?

    Yes, as long as it still has exactly one abstract method. That is how Comparator carries a dozen default methods and still works as a lambda target.

    A lambda is a compact instance of a functional interface. It is not an anonymous class: it compiles to an invokedynamic call site backed by LambdaMetafactory, which means no extra class file per lambda and better JIT inlining. Also, this inside a lambda refers to the enclosing instance, not to the lambda — unlike an anonymous class.

    A lambda captures the local variables it uses, and those must be final or effectively final. The reason is that capture copies the value, so allowing reassignment would create two diverging copies with undefined semantics. Instance and static fields are not captured — they are read through the captured this, so they can change freely.

    The standard workaround when you must mutate captured state is a mutable holder: an AtomicInteger, a one-element array, or better, restructuring to use a stream reduction instead of side effects.

    Java
    int factor = 2;
List<Integer> doubled = nums.stream().map(n -> n * factor).toList();
// factor++;   // would break the lambda above: no longer effectively final

// mutable counter workaround (prefer a reduction where possible)
AtomicInteger seen = new AtomicInteger();
nums.forEach(n -> seen.incrementAndGet());

long better = nums.stream().count();   // no shared mutable state at all
    Follow-ups they will ask

    Why is a lambda cheaper than an anonymous class?

    No class file is generated per lambda (they are spun at runtime and can be shared), a non-capturing lambda is a singleton, and the JIT can inline through the invokedynamic call site more readily.

    What does this mean inside a lambda?

    The enclosing instance. In an anonymous class it means the anonymous instance itself. That difference matters when registering callbacks that reference this.

    A stream pipeline has three parts: a source, zero or more intermediate operations, and one terminal operation. Intermediate operations are lazy — they build up a description and do nothing. Only the terminal operation triggers execution.

    Execution is then fused: elements flow through the whole chain one at a time, rather than each stage materializing a full intermediate collection. That is why filter().map().findFirst() can stop after examining one element, and why the order of filter before map matters for cost.

    Short-circuiting operations — findFirst, findAny, anyMatch, allMatch, limit — stop consuming as soon as the answer is known, which is what makes streams usable on infinite sources like Stream.iterate. And a stream is single-use: consuming it twice throws IllegalStateException.

    Java
    // nothing runs here - no terminal operation
Stream<Order> s = orders.stream().filter(o -> { System.out.println("seen"); return o.isPaid(); });

// fused, short-circuits after the first match
Optional<Order> first = orders.stream()
        .filter(Order::isPaid)
        .map(this::enrich)      // enrich runs only for matching elements
        .findFirst();

Stream.iterate(1, n -> n * 2).limit(10).forEach(System.out::println); // infinite source, bounded
    Follow-ups they will ask

    Why does filter-then-map beat map-then-filter?

    Fusion means map runs once per element that reaches it. Filtering first shrinks the input to the expensive stage. Same result, different cost.

    When are streams the wrong choice?

    Tight numeric loops where the lambda overhead matters, code needing indexes or early exit with complex state, and debugging-heavy logic — a plain loop with a breakpoint is often clearer. Do not use streams for side effects.

  • J51

    Stateless intermediate operations — filter, map, peek — process each element independently and hold nothing between elements. They fuse perfectly and stream lazily.

    Stateful operations — sorted, distinct, limit, skip — must retain information across elements. sorted and distinct are full barriers: sorting has to see every element before it can emit the first one, so laziness stops there and memory grows to the size of the stream.

    Practical consequences: sorted().limit(10) sorts everything before taking ten, so for top-K a bounded priority queue is far better. distinct on an unordered parallel stream is cheaper than on an ordered one, because it need not preserve encounter order. And a stateful op on an infinite stream without a preceding limit never terminates.

    Java
    // sorts the whole list to take 10 - O(n log n), full materialization
List<Order> top = orders.stream()
        .sorted(Comparator.comparing(Order::total).reversed())
        .limit(10).toList();

// O(n log 10) and bounded memory
PriorityQueue<Order> heap = new PriorityQueue<>(Comparator.comparing(Order::total));
for (Order o : orders) { heap.offer(o); if (heap.size() > 10) heap.poll(); }
    Follow-ups they will ask

    Why is peek discouraged outside debugging?

    It is specified for debugging, and implementations may skip it when the result can be computed without traversing every element (for example count() on a sized stream). Using it for side effects makes behaviour version-dependent.

    What does 'encounter order' mean and when can you drop it?

    The defined order of elements in the source. unordered() tells the pipeline you do not need it, which lets parallel distinct and limit use much cheaper algorithms.

    The four-argument toMap(keyFn, valueFn, mergeFn, TreeMap::new) — same for groupingBy with a map factory. Useful when you need sorted or insertion-ordered output.

  • J53

    A Collector is defined by five pieces: supplier (create a fresh mutable container), accumulator (fold one element into it), combiner (merge two containers — used only in parallel), finisher (transform the container into the result), and characteristics (IDENTITY_FINISH, UNORDERED, CONCURRENT).

    The combiner is the part people get wrong, and the bug is invisible in tests: it is never called in a sequential stream, so an incorrect combiner only corrupts results when someone later adds .parallel(). If you cannot write a correct combiner, declare that your collector is sequential-only.

    Before writing one, check whether Collector.of with existing pieces, or reducing, or a downstream combination already covers it — custom collectors are rarer than people think.

    Java
    // join order ids into a bounded, comma-separated summary
Collector<Order, StringJoiner, String> summary = Collector.of(
    () -> new StringJoiner(", ", "[", "]"),        // supplier
    (j, o) -> j.add(o.id()),                        // accumulator
    StringJoiner::merge,                            // combiner (parallel only)
    StringJoiner::toString                          // finisher
);
String s = orders.stream().collect(summary);

    What does IDENTITY_FINISH mean?

    The container is already the result, so the finisher is the identity function and the framework can skip it. toList has it; a collector returning a different type does not.

    When is CONCURRENT safe?

    Only when the container is thread-safe and the accumulator can be called concurrently on it — groupingByConcurrent with a ConcurrentHashMap. It also requires UNORDERED to be useful.

    parallelStream() splits the work across the common ForkJoinPool, which by default has availableProcessors() - 1 threads and is shared by the entire JVM. That single fact drives most of the advice.

If you must, submit the pipeline to your own ForkJoinPool, or simply use an ExecutorService. Always measure; parallel streams are frequently slower.

    A thread moves through NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED. RUNNABLE in Java covers both "running" and "ready to run" — the JVM does not distinguish. BLOCKED means waiting for a monitor lock; WAITING means parked in wait(), join(), or LockSupport.park().

    Runnable returns nothing and cannot throw a checked exception; Callable<V> returns a value and may throw. Submit a Callable to an ExecutorService and you get a Future<V> — and note that an exception thrown inside is captured and only rethrown (wrapped in ExecutionException) when you call get(). A Future you never get() swallows failures silently.

    Interruption is cooperative. t.interrupt() only sets a flag; it does not stop anything. Blocking methods that declare InterruptedException throw it and clear the flag. So if you catch it and cannot propagate, you must restore it with Thread.currentThread().interrupt() — otherwise the cancellation signal is lost and the thread keeps working.

    Java
    while (!Thread.currentThread().isInterrupted()) {
    try {
        queue.take();                       // throws InterruptedException, clears flag
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // restore the flag, then exit
        break;
    }
}
// never do this:
// catch (InterruptedException e) { }   // swallows cancellation entirely

    Why was Thread.stop() deprecated?

    It threw an asynchronous exception at an arbitrary bytecode, leaving objects half-updated and monitors released with broken invariants. There is no safe way to force-stop a thread; cancellation must be cooperative.

    What happens to an uncaught exception in a thread?

    It kills that thread and goes to the thread's UncaughtExceptionHandler (by default printing to stderr). In a thread pool, the worker is replaced — so the failure can be invisible unless you set a handler or inspect the Future.

  • J57

    Every Java object has an intrinsic lock (monitor). synchronized on an instance method locks this; on a static method it locks the Class object; a synchronized(obj) block locks whatever you name. Those are different locks — a common bug is assuming a static and an instance synchronized method exclude each other. They do not.

    Intrinsic locks are reentrant: the owning thread can re-acquire the same lock (a counter is incremented), which is what allows a synchronized method to call another synchronized method on the same object without self-deadlock.

    Lock on a private final object rather than on this or on a public field. Locking on this makes your lock part of your public API — any caller can synchronize on your object and interfere. Never lock on a String literal or a boxed Integer: they are pooled and shared JVM-wide.

    Java
    class Counter {
    private final Object lock = new Object();   // private lock, not `this`
    private int count;

    void inc() { synchronized (lock) { count++; } }

    synchronized void a() { b(); }   // reentrant: b() re-acquires the same monitor
    synchronized void b() { }
}
// static and instance locks are different monitors:
// synchronized void x(){}          locks the instance
// static synchronized void y(){}   locks Counter.class
    Follow-ups they will ask

    Is synchronized slow?

    Not usually. The JVM optimizes uncontended locks heavily, and modern JDKs handle them well. Contention is what costs — and that is a design problem (lock scope, lock granularity), not a keyword problem.

    What does synchronized give you besides mutual exclusion?

    Visibility. Releasing a monitor flushes writes and acquiring it invalidates cached reads, establishing a happens-before edge. Mutual exclusion without visibility would be useless.

  • J58

    The Java Memory Model defines when a write by one thread is guaranteed visible to a read by another. Without it, the compiler, the JIT, and the CPU are all free to reorder and cache — and they do. The JMM is not about locks; it is about which reorderings are legal.

    The central relation is happens-before. If action A happens-before action B, then A's effects are visible to B. The edges you must be able to list: program order within a thread; monitor unlock → subsequent lock of the same monitor; volatile write → subsequent volatile read of the same field; Thread.start() → everything in that thread; everything in a thread → another thread's successful join(); and the constructor's final-field freeze → publication of the reference.

    Without a happens-before edge there is no guarantee at all — not "eventually", not "probably soon". A loop reading a non-volatile flag can be hoisted out by the JIT and spin forever. This is why 'it works on my machine' is meaningless for concurrency: x86 has strong ordering and hides bugs that appear immediately on ARM.

    Java
    // broken: no happens-before edge, may never terminate
boolean running = true;
// thread A:  while (running) { }        // JIT may hoist the read out of the loop
// thread B:  running = false;

// fixed with volatile - establishes the edge
volatile boolean running = true;
    Follow-ups they will ask

    Does happens-before mean "happens earlier in time"?

    No. It is a visibility and ordering guarantee, not a timing one. Two actions can be ordered by happens-before yet execute close together, and unordered actions may still happen to be visible — you just cannot rely on it.

    How does this show up in production?

    Rarely and non-deterministically: a cache that never invalidates, a shutdown flag ignored, a lazily-initialized object seen half-constructed. It typically appears under load, on a different CPU architecture, or after a JIT tier change.

  • J59

    volatile does two things: it guarantees visibility (a write is pushed out and a read is not served from a cached copy) and it forbids reordering across the access, creating a happens-before edge between a write and the subsequent read of that field.

    What it does not give you is atomicity of compound operations. i++ is read-modify-write — three steps. Two threads can both read 5, both write 6, and one increment vanishes. volatile fixes visibility of each individual read and write, not the gap between them.

    So the rule: volatile is right for a flag or a reference that one thread writes and others read — a shutdown signal, a cached configuration reference, the instance field in double-checked locking. For counters use AtomicInteger or LongAdder; for anything involving multiple fields together, use a lock.

    Java
    volatile boolean shutdown = false;      // correct use: single write, many reads

volatile int count;
count++;                                // WRONG - still a race

AtomicInteger safe = new AtomicInteger();
safe.incrementAndGet();                 // correct: single atomic RMW

// volatile also publishes everything written before it
config = newConfig;                     // if `config` is volatile, readers see a
                                        // fully-initialized newConfig
    Follow-ups they will ask

    Why does a volatile write publish other, non-volatile writes?

    Because the volatile write acts as a release barrier: everything written before it in program order is visible to any thread that subsequently reads that volatile field. This is what makes safe publication via a volatile reference work.

    Is volatile cheaper than synchronized?

    A volatile read is nearly free; a volatile write costs a memory fence. It is cheaper than locking but only solves visibility — using it where you need atomicity is the classic wrong optimization.

  • J60

    Safe publication means making an object visible to other threads in a fully-constructed state. The unsafe version — assigning to a plain field — allows another thread to see the reference before the constructor's writes, so it observes default values.

    The safe ways: initialize it from a static initializer; store it into a volatile field or an AtomicReference; store it into a field guarded by a lock; or put it into a thread-safe collection. Or make the object immutable with all-final fields — the final field freeze guarantees any thread seeing the reference sees the finals correctly initialized, with no synchronization at all.

    Double-checked locking is the classic example. It was broken before Java 5 and is correct now only if the field is volatile — without it, the reference can be published before the constructor completes. Honestly, prefer the holder idiom: it is simpler, lazy, and needs no volatile.

    Java
    // correct DCL - volatile is mandatory
class Registry {
    private static volatile Registry instance;
    static Registry get() {
        Registry r = instance;                  // one volatile read on the fast path
        if (r == null) {
            synchronized (Registry.class) {
                r = instance;
                if (r == null) instance = r = new Registry();
            }
        }
        return r;
    }
}

    private static class H { static final Registry2 I = new Registry2(); }
    static Registry2 get(){ return H.I; }
}

    Why exactly does DCL fail without volatile?

    instance = new Registry() is allocate, construct, assign — and the JIT may reorder assign before construct. Another thread sees a non-null reference to a half-built object. volatile forbids that reordering.

    When is the holder idiom not enough?

    When the singleton needs constructor arguments known only at runtime, or when you need to reset it in tests. Then use dependency injection instead of a singleton at all.

  • J61

    The atomic classes wrap a compare-and-swap (CAS) CPU instruction: "if this memory location still holds the value I expect, replace it, atomically". Failure is not an error — you retry in a loop. That is optimistic concurrency: no blocking, no context switch, but wasted CPU under heavy contention.

    AtomicInteger.incrementAndGet is exactly that loop. The general form is updateAndGet(fn), and it is where a subtle rule applies: the function may be invoked multiple times if the CAS keeps failing, so it must be pure and side-effect-free.

    The ABA problem: a CAS only checks the value, not the history. If another thread changes A→B→A, your CAS succeeds even though the world changed underneath — which matters for lock-free stacks where the node was recycled. AtomicStampedReference adds a version counter so you compare value and stamp.

    Java
    AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();

// the function may run more than once - keep it pure
AtomicReference<Config> ref = new AtomicReference<>(initial);
ref.updateAndGet(c -> c.withRetries(c.retries() + 1));

// ABA-safe
AtomicStampedReference<Node> head = new AtomicStampedReference<>(n, 0);
int[] stamp = new int[1];
Node cur = head.get(stamp);
head.compareAndSet(cur, next, stamp[0], stamp[0] + 1);
    Follow-ups they will ask

    When does CAS beat a lock, and when does it lose?

    CAS wins at low-to-moderate contention (no context switch, no scheduler involvement). At high contention the retry loop burns CPU while making no progress, and a lock — which parks the thread — can be faster. Measure.

    Is a CAS loop lock-free or wait-free?

    Lock-free: the system as a whole always makes progress, but an individual thread can starve by losing every race. Wait-free would bound each thread's steps, which CAS loops do not.

  • J62

    AtomicLong under heavy write contention degrades badly: every thread CASes the same memory word, so they invalidate each other's cache lines and most attempts fail and retry. This is the classic hot-counter problem in a high-throughput service.

    LongAdder solves it by striping: it keeps a base value plus an array of per-thread cells. Each thread updates its own cell, so writes rarely collide. sum() then adds up all cells — which means reads are more expensive and give a value that is not a consistent instantaneous snapshot.

    So the rule: LongAdder for write-heavy, read-rare counters (metrics, request counts); AtomicLong when you read often or need the exact value at a moment (a sequence generator, a semaphore-like limit). Underneath both sits false sharing — unrelated variables on the same 64-byte cache line ping-ponging between cores — which @Contended padding addresses and which LongAdder's cells already avoid.

    Java
    // write-heavy metric: LongAdder
private final LongAdder requests = new LongAdder();
requests.increment();          // contention-free in the common case
long total = requests.sum();   // aggregate over the cells

// needs an exact, immediately-readable value: AtomicLong
private final AtomicLong sequence = new AtomicLong();
long next = sequence.incrementAndGet();
    Follow-ups they will ask

    What is false sharing, concretely?

    Two variables written by different cores land in the same cache line. Each write invalidates the other core's copy, so the line bounces between caches even though the variables are unrelated. Padding to a cache line apart removes it.

    Why is LongAdder.sum() not exact under concurrency?

    It walks the cells without locking, so updates during the walk may or may not be included. It is eventually consistent, which is exactly right for metrics and wrong for a sequence.

  • J63

    ReentrantLock does everything synchronized does, plus the things it cannot: tryLock() (give up immediately), tryLock(timeout) (give up after a while — the standard deadlock escape), lockInterruptibly(), optional fairness, multiple Conditions on one lock, and acquiring in one method while releasing in another.

    The cost is that you must unlock() in a finally — forgetting it leaks the lock permanently. Fairness sounds attractive but is expensive: it enforces FIFO handoff and roughly halves throughput, so use it only when starvation is a demonstrated problem.

    ReadWriteLock allows many concurrent readers or one writer. It only pays off when reads are long and writes are rare; otherwise the extra bookkeeping makes it slower than a plain lock, and naive implementations can starve writers. StampedLock adds optimistic reads — take a stamp, read without locking, then validate; if a write intervened, fall back to a real read lock. It is faster but not reentrant, and misuse deadlocks.

    Java

if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {

} else {
    metrics.lockTimeout();                          // back off instead of blocking
}

}

    When would you choose synchronized over ReentrantLock?

    Almost always, for simple mutual exclusion — it is harder to misuse (no forgotten unlock), reads better, and performs comparably. Reach for ReentrantLock only when you need one of its extra capabilities.

    What is a Condition and why is it better than wait/notify?

    A Condition is a wait-set bound to a Lock. Multiple Conditions on one lock let you signal precisely — notFull and notEmpty in a bounded queue — instead of notifyAll waking every waiter to re-check.

    A ThreadPoolExecutor is defined by corePoolSize, maximumPoolSize, keepAliveTime, the work queue, the thread factory, and the rejection policy — and the interaction between them is counter-intuitive, which is exactly what gets asked.

    The submission algorithm is: if fewer than core threads exist, create one. Otherwise try to queue. Only if the queue is full do you create threads up to maximum. If the queue is full and maximum is reached, reject. The consequence: with an unbounded queue, the queue never fills, so maximumPoolSize is never reached — the pool silently stays at core size and the queue grows until you OOM. That is exactly what Executors.newFixedThreadPool and newSingleThreadExecutor do.

    So: always construct ThreadPoolExecutor directly with a bounded queue and a deliberate rejection policy. AbortPolicy (default) throws; CallerRunsPolicy executes on the submitting thread, which is a natural backpressure mechanism because it slows the producer; DiscardPolicy/DiscardOldestPolicy lose work silently and are rarely right.

    Java
    ExecutorService pool = new ThreadPoolExecutor(
        8, 16, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),             // BOUNDED
        new ThreadFactoryBuilder().setNameFormat("orders-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy()); // backpressure

// shutdown properly
pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) pool.shutdownNow();

    Because a thread dump with 200 threads called pool-3-thread-17 is unreadable. Named pools turn a production stack dump into an immediate diagnosis.

    For CPU-bound work the right size is roughly availableProcessors(), sometimes +1 to cover an occasional page fault. More threads than cores does not create more CPU; it just adds context switching and cache pressure.

    For IO-bound work threads spend most of their time blocked, so you want more of them. The classic formula is threads = cores × targetUtilization × (1 + waitTime/serviceTime). If a call waits 100ms and computes 5ms on 8 cores at full utilization, that is 8 × 21 ≈ 168 threads.

    But the honest modern answer has two extra parts. First, the pool is not the only limit — a 200-thread pool in front of a 20-connection HikariCP pool just moves the queue. Size the whole chain together. Second, virtual threads change this: for IO-bound work you no longer size a pool at all, you use newVirtualThreadPerTaskExecutor() and bound concurrency with a semaphore where the downstream needs protecting.

    Java

ExecutorService cpu = Executors.newFixedThreadPool(cores);   // CPU-bound

// IO-bound, modern approach
var io = Executors.newVirtualThreadPerTaskExecutor();
Semaphore downstreamLimit = new Semaphore(50);   // protect the slow dependency

// container-aware: availableProcessors respects cgroup CPU limits on modern JDKs

    What is the failure mode of a pool that is too large?

    Memory (each platform thread reserves ~1MB of stack), context-switch overhead, and — worst — overwhelming a downstream dependency that then times out, converting your excess capacity into a cascading failure.

    Should every task type share one pool?

    No. Separate pools per dependency is the bulkhead pattern: a slow payment provider then cannot exhaust the threads your health check needs.

    ScheduledExecutorService replaces Timer: it uses a pool (so one slow task does not block all others), and a task throwing an exception does not kill the scheduler — whereas a single Timer thread dies on an uncaught exception and every later task silently never runs.

    Know the difference between the two repeating modes. scheduleAtFixedRate fires every period regardless of how long the task takes — if the task overruns, executions bunch up back-to-back. scheduleWithFixedDelay waits delay after each completion, so it never overlaps and never bunches. For most polling and cleanup jobs, fixed-delay is what you actually want.

    The critical operational detail: if a scheduled task throws, all future executions of that task are cancelled — silently. Always wrap the body in try/catch and log. This is one of the most common "our background job just stopped working weeks ago" incidents.

    Java
    ScheduledExecutorService s = Executors.newScheduledThreadPool(2);

s.scheduleWithFixedDelay(() -> {
    try {
        reconcile();
    } catch (Exception e) {                 // MANDATORY - otherwise no more runs
        log.error("reconcile failed", e);
    }
}, 0, 5, TimeUnit.MINUTES);
    Follow-ups they will ask

    Why not use this for business-critical scheduling?

    It is in-memory and per-instance: it does not survive a restart, and with N replicas the job runs N times. Use a persistent scheduler (Quartz with a DB, or a distributed scheduler with leases) plus leader election.

    How do you make a scheduled job safe across replicas?

    A distributed lock or lease with a TTL (Redis, or a DB row with a fencing token), acquired at the start of each run and released at the end. The job must also be idempotent, because leases can expire mid-run.

    CompletableFuture composes asynchronous steps without blocking.     Always pass an explicit executor. The no-arg async methods use the common ForkJoinPool — shared JVM-wide and sized to cores — so any blocking call inside starves everything else. Pass your own pool and name its threads.

    Exceptions propagate down the chain and short-circuit it: thenApply stages are skipped, while handle and whenComplete still run. Use exceptionally to recover with a fallback value, handle to see both outcomes. The silent killer is a failed future nobody joins — the exception simply vanishes, so always terminate a chain with a handler or a logged whenComplete.

    Java

    Java 8 rewrote ConcurrentHashMap.     Iterators are weakly consistent: they never throw ConcurrentModificationException, traverse elements as of some point at or after creation, and never return an element twice.     CopyOnWriteArrayList makes every mutation copy the entire backing array.     Note the iterator consequence: iterator.remove() throws UnsupportedOperationException, because the snapshot is immutable. And be honest about the tradeoff in an interview — naming the write cost is what shows you understand it rather than having memorized the name.

    CopyOnWriteArraySet, backed by the same array — so contains is O(n), not O(1). Fine for a handful of elements, wrong for thousands.

    BlockingQueue is the backbone of producer-consumer designs: put blocks when full, take blocks when empty, so flow control is built in and you never hand-write wait/notify.

    The implementations differ in ways worth knowing. ArrayBlockingQueue — bounded, single lock, array-backed, predictable memory. LinkedBlockingQueue — optionally bounded (unbounded by default, which is the OOM trap), separate put/take locks so higher throughput. SynchronousQueue — capacity zero: a handoff where the producer waits for a consumer; this is what newCachedThreadPool uses. PriorityBlockingQueue — unbounded, ordered by comparator.     Also know the four method families, because interviewers ask: throws (add/remove), returns special value (offer/poll), blocks (put/take), and times out (offer(t,u)/poll(t,u)).

    Java
    BlockingQueue<Task> q = new ArrayBlockingQueue<>(1000);   // bounded = backpressure

    Why is an unbounded queue a design smell?

    It converts backpressure into memory growth. The system appears healthy while the queue silently grows, then dies with an OOM — far worse than rejecting work early with a clear signal.

    How would you implement a bounded queue yourself?

    A ReentrantLock with two Conditions, notFull and notEmpty; wait in a while loop (spurious wakeups are real), signal the opposite condition after each operation. Getting the while-loop and the two conditions right is the whole exercise.

    CountDownLatch is a one-shot gate: threads await() until the count reaches zero. Once it does, it stays open forever — you cannot reset it. Use it to wait for N parallel initializations, or as a start gate in tests.

    CyclicBarrier is reusable and symmetric: N threads each call await() and all are released together, optionally running a barrier action first. Use it for iterative parallel algorithms where every worker must finish phase K before any starts K+1.

    Semaphore bounds concurrent access to a resource — acquire/release permits. It is the standard way to limit concurrent calls to a slow dependency, and it is what you pair with virtual threads to cap downstream load.     Latch or barrier — how do you pick?

    Latch when one set of threads waits for a different set to finish (one-shot, asymmetric). Barrier when the same set of threads must rendezvous repeatedly (reusable, symmetric).

    Everyone waits forever unless you use the timed await. If a waiting thread is interrupted or times out, the barrier is broken and all other waiters get BrokenBarrierException — a deliberate fail-fast.

    Deadlock needs four conditions simultaneously: mutual exclusion, hold-and-wait, no preemption, and circular wait. Break any one and it cannot happen. In practice you break circular wait by imposing a global lock ordering — always acquire locks in the same order, for example by object id or hash.

    The alternatives: tryLock with a timeout and backoff (breaks hold-and-wait — you release everything and retry), or redesigning so only one lock is needed at a time. Livelock is threads actively responding to each other and making no progress — usually retry loops without randomized backoff. Starvation is a thread never getting the resource, typically under an unfair lock or a priority scheme.

    Detection in production is straightforward and worth being able to state precisely: jstack <pid> or jcmd <pid> Thread.print prints "Found one Java-level deadlock" with both stacks and the lock identities. Programmatically, ThreadMXBean.findDeadlockedThreads() can feed a health check.

    Java
    // classic deadlock: two accounts, two orders
void transfer(Account a, Account b, long amt) {
    synchronized (a) { synchronized (b) { a.debit(amt); b.credit(amt); } }
}
// transfer(x,y) and transfer(y,x) concurrently -> circular wait

// fix: global ordering by identity
void transferSafe(Account a, Account b, long amt) {
    Account first  = a.id() < b.id() ? a : b;
    Account second = a.id() < b.id() ? b : a;
    synchronized (first) { synchronized (second) { a.debit(amt); b.credit(amt); } }
}
    Follow-ups they will ask

    What if two accounts have equal ids?

    Fall back to System.identityHashCode and, if those also collide, use a third "tie-breaker" lock acquired first. The JDK's own ConcurrentHashMap and many bank examples use exactly this three-step scheme.

    How would you catch this before production?

    Enforce lock ordering by construction (a single lock-acquisition helper), keep lock scopes tiny, never call foreign or blocking code while holding a lock, and add a periodic findDeadlockedThreads check to your health endpoint.

  • J73

    ThreadLocal gives each thread its own copy of a value — legitimately used for per-request context (trace id, tenant, security principal, MDC in logging) and for non-thread-safe objects you want to reuse, like the old SimpleDateFormat.

    In a thread pool it becomes a leak and a correctness bug. Threads are reused, so a value set during request A is still there for request B — leaking data across requests, which in a multi-tenant system is a security incident. And because the entry is held by the thread, the value never becomes garbage while the pool lives. The rule is always remove() in a finally.

    On modern JDKs, ScopedValue is the replacement: the value is bound for the dynamic extent of a call and automatically unbound afterwards, so it cannot leak, it is immutable, and it works correctly with virtual threads and structured concurrency.

    Java
    private static final ThreadLocal<String> TRACE = new ThreadLocal<>();

void handle(Request r) {
    TRACE.set(r.traceId());
    try { process(r); }
    finally { TRACE.remove(); }      // MANDATORY in a pooled thread
}

// modern equivalent - cannot leak
// ScopedValue.where(TRACE, r.traceId()).run(() -> process(r));
    Follow-ups they will ask

    Why do the internal entries use weak references but still leak?

    The key (the ThreadLocal object) is weakly referenced, but the value is strongly held by the thread's map until the slot is cleaned. With a static ThreadLocal the key never dies, so nothing is ever cleaned — hence remove().

    What breaks with ThreadLocal and virtual threads?

    Nothing functionally, but with millions of virtual threads a per-thread copy is expensive, and inheritable thread-locals multiply that. ScopedValue exists precisely to make per-request context cheap at that scale.

  • J74

    A virtual thread is a lightweight thread managed by the JVM, not the OS. Millions can exist; each is a heap object with a growable stack, mounted onto a small pool of OS carrier threads only while running. When it blocks on IO, it unmounts, freeing the carrier — so blocking code stops being expensive.

    What changes practically: thread-per-request becomes viable again for IO-bound services, with ordinary readable code and real stack traces, at throughput comparable to reactive frameworks. What does not change: virtual threads give you no extra CPU, so CPU-bound work still needs a bounded pool sized to cores.

    The pitfalls are worth naming. Do not pool virtual threads — they are cheap to create; use newVirtualThreadPerTaskExecutor. Pinning happens when a virtual thread blocks inside a synchronized block or a native frame: it cannot unmount and holds the carrier. Recent JDKs largely fixed the synchronized case, but the safe pattern is ReentrantLock in code that blocks. And since concurrency is now unbounded, you must add explicit limits (a Semaphore) to protect downstream systems.

    Java
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var req : requests) exec.submit(() -> handle(req));   // millions is fine
}

// pinning risk: blocking inside synchronized holds the carrier
// synchronized (lock) { httpClient.send(...); }   // avoid
ReentrantLock lock = new ReentrantLock();          // prefer - unmounts correctly

// concurrency is now unbounded - protect the dependency yourself
Semaphore db = new Semaphore(50);
    Follow-ups they will ask

    When are platform threads still the right answer?

    CPU-bound work (sized to cores), work needing thread priorities or affinity, and long-running native calls that would pin a carrier anyway.

    Does Loom remove the need for reactive programming?

    For most request/response services, yes — it removes the main reason people adopted reactive, which was thread efficiency. Reactive still earns its place for streaming with explicit backpressure and complex event composition.

  • J75

    Structured concurrency applies the block-scope discipline of ordinary code to concurrent tasks: subtasks forked inside a scope must all complete before the scope exits. It makes concurrency a tree rather than a tangle of loose futures.

    The payoff is error handling and cancellation. With a StructuredTaskScope, if one subtask fails the others are automatically cancelled; if the parent is interrupted, the children are too; and no subtask can outlive the scope, so there are no orphaned threads leaking work. The two built-in policies are ShutdownOnFailure (all must succeed — the fan-out-and-join case) and ShutdownOnSuccess (first wins — hedged requests).

    Compare with CompletableFuture.allOf: that also fans out, but a failure does not cancel siblings, the relationships are invisible in a stack trace, and it is easy to leak a future nobody joins. Structured concurrency makes the lifetime explicit and observable.

    Java
    // fan out to two services; either failure cancels the other
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> userService.find(id));
    var prefs = scope.fork(() -> prefsService.find(id));

    scope.join();            // wait for both (or the first failure)
    scope.throwIfFailed();   // propagate the failure

    return new Profile(user.get(), prefs.get());
}   // nothing escapes this block
    Follow-ups they will ask

    What problem does it fix that CompletableFuture does not?

    Leaked and orphaned tasks, and cancellation propagation. With CF, a failed branch leaves siblings running and burning resources unless you wire cancellation manually.

    Is it stable API?

    It has been in preview across several JDK releases and the shape has changed between them — check the API for your exact JDK version before relying on it in production.

  • J76

    The Fork/Join framework targets divide-and-conquer: split a task recursively until pieces are small enough, compute, and merge. RecursiveTask<V> returns a value, RecursiveAction does not.

    Its distinguishing mechanism is work stealing. Each worker has its own double-ended queue: it pushes and pops its own subtasks from one end (LIFO, good for cache locality), and idle workers steal from the other end of a busy worker's queue (FIFO, stealing the largest, oldest chunk). That keeps all cores busy without a central queue becoming a bottleneck.

    The idiomatic shape matters: fork one half, compute the other half on the current thread, then join. Forking both halves wastes a thread that could have done work. And the threshold below which you stop splitting is a real tuning parameter — too small and coordination dominates. Parallel streams run on this machinery, so understanding it explains their behaviour.

    Java
    class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;
    private final long[] a; private final int lo, hi;
    SumTask(long[] a, int lo, int hi){ this.a=a; this.lo=lo; this.hi=hi; }

    @Override protected Long compute() {
        if (hi - lo <= THRESHOLD) {
            long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        left.fork();                                  // hand off one half
        long right = new SumTask(a, mid, hi).compute();// do the other half here
        return left.join() + right;
    }
}
    Follow-ups they will ask

    Why is stealing FIFO while local access is LIFO?

    LIFO locally keeps the hottest, most recently split data in cache. Stealing from the opposite end takes the oldest, largest task, which minimizes the number of steals needed to spread the work.

    What must you never do inside a Fork/Join task?

    Block on IO or a lock. It occupies a worker that cannot then steal, and in the shared common pool it starves the whole JVM. If unavoidable, wrap it in a ManagedBlocker so the pool can compensate.

    Classes are loaded by a hierarchy of loaders: bootstrap (core JDK), platform (JDK modules), and application (your classpath). The delegation model means each loader asks its parent first and only loads the class itself if the parent cannot. That is what stops you from replacing java.lang.String with your own.

    Application servers and plugin systems invert this (child-first) so each deployed app can carry its own library versions — which is also where most classloader pain comes from: the same class name loaded by two loaders produces two distinct runtime classes, and casting between them throws a ClassCastException that reads like nonsense ("cannot cast Foo to Foo").

    A classloader leak is the classic redeploy problem: something with a longer lifetime than the app — a static field in a parent-loaded class, a running thread, a ThreadLocal, a JDBC driver registration, a shutdown hook — holds a reference to a class loaded by the app's loader. That pins the loader, and with it every class it loaded. It shows up as Metaspace growth across redeploys, not heap growth.

    Java

// -XX:+UnlockDiagnosticVMOptions -XX:+PrintClassHistogram

    Why does the leak show as Metaspace, not heap?

    Class metadata lives in Metaspace (native memory since Java 8, replacing PermGen). A pinned loader keeps its classes' metadata alive, so you get OutOfMemoryError: Metaspace after a few redeploys while the heap looks healthy.

    How do you confirm which loader is pinned?

    Take a heap dump, find the ClassLoader instances, and follow the GC-root path to see what holds them. It almost always terminates at a static field or a live thread outside the app.

  • J78

    Loading is only the first step. Linking follows: verification (the bytecode verifier proves type safety, stack discipline, and that no instruction jumps somewhere illegal), preparation (static fields get default values — zero/null, not their initializers), and resolution of symbolic references, which is lazy in HotSpot.

    Then initialization runs <clinit> — static field initializers and static blocks — and it happens exactly once, lazily, on first active use. The JVM guarantees this with a per-class initialization lock, so two threads racing to touch a class cannot both run the static initializer.

    That guarantee is what the holder idiom exploits: a lazily-initialized singleton with no synchronization in your code, because the JVM already does it. And it explains a debugging trap — a class with only compile-time constants may never initialize at all, since constants are inlined into callers at compile time.

    Java
    class Config {
    private Config() { /* expensive */ }
    private static class Holder {          // not loaded until Holder is touched
        static final Config INSTANCE = new Config();
    }
    static Config get() { return Holder.INSTANCE; }   // thread-safe, lazy, lock-free
}

class A { static final int X = 42; }       // compile-time constant
// int y = A.X;   does NOT initialize A - the 42 is inlined by javac
    Follow-ups they will ask

    What is verification protecting you from?

    Hand-crafted or corrupted bytecode that would violate memory safety — bad casts, stack underflow, jumping into the middle of an instruction. It is why the JVM can run untrusted bytecode without the whole thing being unsafe.

    What if two threads call get() simultaneously the first time?

    One wins the class-init lock and runs the initializer; the other blocks until it completes and then sees the fully constructed instance. This is a JVM-level guarantee, not something your code has to arrange.

    The runtime data areas: the heap (all objects, GC-managed, shared), Metaspace (class metadata, native memory, unbounded by default), one stack per thread (frames, locals, ~1MB reserved each), the code cache (JIT-compiled native code), and direct/native memory (NIO buffers, some libraries).

    The operationally important point is that heap is not the process's memory footprint. Total RSS ≈ heap + metaspace + thread stacks + code cache + direct buffers + GC structures + native allocations. Setting -Xmx equal to the container limit is therefore a reliable way to get OOMKilled with a perfectly healthy heap graph.

    Know the failure signature of each: heap exhaustion → OutOfMemoryError: Java heap space; a classloader leak → Metaspace; too many threads → unable to create native thread; leaked ByteBuffers → Direct buffer memory; deep recursion → StackOverflowError.

    Why prefer MaxRAMPercentage to -Xmx in containers?

    It adapts if the container limit changes and keeps a deliberate fraction for non-heap memory. Hardcoding -Xmx means every limit change needs a code change, and people forget.

    Available memory divided by the per-thread stack reservation (-Xss), plus the OS thread limit. Reducing -Xss lets you create more threads — or use virtual threads and stop worrying.

  • J80

    Every object has a header: a mark word (identity hash, GC age, lock state) plus a class pointer — 12 bytes with compressed oops on a 64-bit JVM, and objects are padded to an 8-byte boundary. So the smallest object is 16 bytes, and an Integer costs 16 bytes to hold 4 bytes of data.

    Compressed oops store 32-bit offsets instead of 64-bit pointers, cutting reference size in half. They work up to about a 32GB heap — which is why a 31GB heap can hold more objects than a 33GB heap. If you need more than ~32GB, know that you just lost compression and check whether you really do.

    The practical consequences show up in data-heavy code: Integer[] costs roughly six times int[]; a HashMap entry is an object with four fields plus the boxed key and value; a linked structure pays a header per node. This is the concrete reason to prefer primitive arrays and specialized streams in hot paths.

    Java
    // use JOL to see actual layout rather than guessing
// org.openjdk.jol.info.ClassLayout.parseInstance(obj).toPrintable();

// long[1_000_000]        ~  8 MB
// Long[1_000_000]        ~ 24 MB  (8MB refs + 16MB objects)
// ArrayList<Long> same   ~ 24 MB + list overhead
    Follow-ups they will ask

    Why does the 32GB heap threshold exist?

    Compressed oops encode a reference as a 32-bit value scaled by the 8-byte alignment, giving 2^32 × 8 = 32GB of addressable heap. Beyond that the JVM must use full 64-bit pointers, increasing memory use by roughly 20%.

    What is the mark word used for besides the hash?

    Lock state (biased/thin/fat), GC age and forwarding pointers during collection. It is why calling identityHashCode on an object can interact with locking optimizations.

  • J81

    Escape analysis is a JIT optimization that determines whether an object created in a method can be seen outside it. If it cannot escape, three optimizations become legal.

    Scalar replacement: the object is never allocated at all — its fields become local variables in registers. Stack allocation: allocate in the frame, freed on return with no GC involvement. Lock elision: if an object is provably thread-confined, synchronization on it is removed entirely (which is why using StringBuffer locally costs little — the locks get elided).

    This is why "avoid allocation" advice is often wrong for short-lived local objects: the JIT frequently removes them. It also explains why a micro-optimization can vanish under a profiler — and why returning or storing an object in a field can silently cost you the optimization by making it escape.

    Java
    // point never escapes -> likely scalar-replaced, zero allocation
double dist(double x1,double y1,double x2,double y2){
    Point a = new Point(x1,y1), b = new Point(x2,y2);
    return Math.hypot(a.x-b.x, a.y-b.y);
}

// see it happen:
// -XX:+UnlockDiagnosticVMOptions -XX:+PrintEscapeAnalysis -XX:+PrintEliminateAllocations
    Follow-ups they will ask

    Why can you not rely on escape analysis?

    It is a best-effort JIT optimization: it needs the allocation site to be inlined and the analysis to succeed, both of which depend on profile data and inlining budgets. Design for correctness and measure; do not assume.

    Does it work across method boundaries?

    Only after inlining. If the method containing the allocation is too big to inline, or the object is passed to a virtual call the JIT cannot devirtualize, the object escapes and is allocated normally.

  • J82

    GC rests on the generational hypothesis: most objects die young. So the heap is split into a young generation (Eden plus two survivor spaces) and an old generation. New objects go in Eden; a minor GC collects the young gen, copying the few survivors between survivor spaces and promoting long-lived ones to old.

    Because most objects die, a minor GC only has to trace and copy the small live set — collection cost is proportional to live data, not to garbage. That is why allocating many short-lived objects is genuinely cheap in Java, and why object pooling is usually counterproductive.

    A major/full GC collects the old generation and is far more expensive. The pathologies to recognize: a promotion rate so high that objects are promoted before they die (survivor spaces too small, or genuinely long-lived data), and humongous allocations in G1 — objects larger than half a region that go straight to old, fragmenting it.

    Java
    // log GC and look at what is actually happening
// -Xlog:gc*:file=gc.log:time,uptime,level,tags

// signals to read from the log:
//   frequent full GCs                -> old gen pressure or a leak
//   promotion failures / to-space exhausted -> survivors too small, bump ratios
//   long pauses growing over time     -> fragmentation or a growing live set
    Follow-ups they will ask

    Why is object pooling usually a bad idea in Java?

    Pooled objects survive, so they get promoted to old gen and are traced on every collection — you convert cheap young-gen garbage into expensive long-lived data, and add synchronization on the pool. Pool only genuinely expensive resources (connections, threads).

    What is a write barrier and why does it exist?

    Generational GC must know when an old-gen object references a young-gen one, or minor GC would miss live objects. A write barrier records those cross-generational references in a remembered set — a small cost on every reference write.

    Serial — one thread, stop-the-world, ideal for tiny heaps and single-CPU containers. Parallel — multi-threaded stop-the-world, maximum throughput, long pauses; right for batch jobs where total time matters more than latency. CMS — historic concurrent old-gen collector, removed in JDK 14; know the name and that fragmentation was its weakness.

    G1 is the default since Java 9. The heap is divided into equal-sized regions, each dynamically young or old. It concurrently marks liveness, then collects the regions with the most garbage first (hence Garbage-First), choosing how many to fit within your MaxGCPauseMillis target. That target is a goal, not a guarantee.

    ZGC and Shenandoah are the low-latency collectors: concurrent compaction using load/store barriers, sub-millisecond pauses largely independent of heap size (ZGC handles terabytes). You trade a few percent of throughput and some extra memory for pause times that stop mattering. Choose by requirement: throughput → Parallel; balanced default → G1; strict latency SLO → ZGC.

    When would you move off G1 to ZGC?

    When p99 latency is dominated by GC pauses and you have measured it — typically large heaps (>16GB) with a strict tail-latency SLO. Do not switch on intuition; compare pause histograms under real load.

    Does a bigger heap always mean fewer GCs?

    Fewer, but each old-gen collection traces a larger live set, so pauses grow with non-generational collectors. With ZGC that matters much less, which is the point of concurrent compaction.

    Tuning starts with a goal, not a flag. Decide whether you are optimizing throughput (total work per unit time) or latency (pause length at p99), because they trade against each other.     OutOfMemoryError is not one condition — the message tells you which resource ran out, and each has a different fix. Reading the message is the first diagnostic step.

    The JVM starts by interpreting bytecode, profiling as it goes. Tiered compilation then escalates hot methods: C1 compiles quickly with instrumentation, and once a method is hot enough, C2 compiles it aggressively using the collected profile.

    Inlining is the enabling optimization — it pastes a callee's body into the caller, which then unlocks constant folding, escape analysis, and lock elision. Methods above a bytecode size threshold are not inlined, which is a real argument for keeping hot methods small. Virtual calls are devirtualized when the profile shows only one or two receiver types.

    Deoptimization is the flip side: optimizations are speculative, guarded by cheap checks. If a new class breaks the monomorphic assumption, or an uncommon branch is finally taken, the JVM discards the compiled code and falls back to the interpreter, then recompiles. This is why performance can change minutes into a run, and why warmup is real: a freshly started pod is genuinely slower and should receive traffic gradually.

    Why does a megamorphic call site hurt?

    With three or more receiver types the JIT cannot devirtualize, so the call stays an indirect jump, blocks inlining, and prevents downstream optimizations. This is a real cost of deep interface hierarchies in hot loops.

    How does this affect your deployment strategy?

    New instances should ramp traffic gradually (slow start on the load balancer) or be pre-warmed with synthetic requests. Sending full production traffic to a cold JVM causes a latency spike and sometimes a cascading timeout.

    It means you are not actually CPU-bound — you are probably seeing pool exhaustion or GC. Check the GC log and connection pool metrics; blocked threads waiting on IO should show low CPU, so the accounting is telling you to look elsewhere.

    A naive microbenchmark almost always lies, for four specific reasons: no warmup (you measure the interpreter), dead-code elimination (the JIT deletes a computation whose result you never use), constant folding (a loop-invariant input gets precomputed), and on-stack replacement plus profile pollution from an unrepresentative loop.

    JMH exists to defeat all of those: it runs warmup iterations, forks fresh JVMs (so one benchmark's profile does not pollute another's), and gives you Blackhole to consume results and @State to keep inputs opaque to the compiler. Returning a value from the benchmark method is the simplest way to avoid elimination.

    The interview-worthy point is the reasoning, not the API: measure at the level that matters. A 5% win in a microbenchmark that sits behind a 40ms database call is worth nothing. Profile first to find where the time actually goes, then benchmark only that.

    Java
    @BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5) @Measurement(iterations = 10) @Fork(2)
@State(Scope.Benchmark)
public class HashBench {
    private List<String> data;      // @State keeps it opaque to the JIT

    @Setup public void setup() { data = generate(10_000); }

    @Benchmark public int hashing() {
        int h = 0;
        for (String s : data) h ^= s.hashCode();
        return h;                   // returned, so it cannot be eliminated
    }
}
    Follow-ups they will ask

    Why does JMH fork a new JVM per trial?

    To isolate profile pollution. If benchmark A ran first and made a call site megamorphic, benchmark B inherits a worse compilation. Forking gives each a clean profile.

    When is a microbenchmark the wrong tool entirely?

    When the question is about a system, not a method — throughput under concurrency, latency under GC, behaviour with a cold cache. Use a load test against the real service for those.

    Modern JVMs are container-aware: availableProcessors() respects the cgroup CPU quota and the default heap is a percentage of the container limit, not the host's RAM. On older JVMs (before 8u191/10) they saw the host, which is how a 2GB-limited pod would try to size a 32GB heap and die instantly.

    The OOMKilled trap comes from forgetting that heap is only part of the process. If the container limit is 1GB and you set -Xmx1g, then metaspace, thread stacks, code cache, direct buffers and GC structures push RSS past the limit and the kernel kills the process — with no Java OutOfMemoryError, no heap dump, and nothing in your logs. Just exit code 137.

    So: set -XX:MaxRAMPercentage to roughly 60–75%, cap Metaspace and direct memory explicitly, and remember that CPU limits also throttle GC threads — a container limited to 1 CPU with a GC sized for 8 will have terrible pauses. Learn to recognize exit code 137 as "the kernel killed you", not "the app crashed".

    Java
    # a sane container baseline
JAVA_OPTS="-XX:MaxRAMPercentage=70 \
           -XX:MaxMetaspaceSize=256m \
           -XX:MaxDirectMemorySize=256m \
           -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
           -XX:+ExitOnOutOfMemoryError"

# kubectl describe pod -> Last State: Terminated, Reason: OOMKilled, Exit Code: 137
    Follow-ups they will ask

    How do you tell an OOMKill from a Java OOM?

    Java OOM: an OutOfMemoryError in your logs, a heap dump, and the JVM chooses to die. OOMKill: no application log at all, exit code 137, and the reason visible only in the pod/container status. Different causes, different fixes.

    Why can a CPU limit make latency worse than a smaller limit would suggest?

    cgroup CPU quota throttles the whole process in periods. GC threads, JIT compiler threads and your request threads all compete for the quota, so a burst of compilation or a GC cycle can consume the period and stall requests entirely.

  • J91

    Java serialization turns an object graph into bytes with almost no code. It is discouraged because of how it does it: deserialization constructs objects without running their constructors, so every invariant your constructor enforces is bypassed, and the byte stream itself decides which classes get instantiated.

    That is the attack surface. A crafted stream can drive a chain of readObject calls through classes already on your classpath ("gadget chains") into arbitrary code execution — the root cause of a long line of critical CVEs in widely used libraries. Never deserialize untrusted input. If you must, use a serialization filter (ObjectInputFilter) to allowlist classes.

    serialVersionUID is the compatibility contract: if you do not declare it, the compiler derives one from the class structure, so any change to fields or methods breaks deserialization of old data with InvalidClassException. Declare it explicitly on anything you serialize. In practice, prefer an explicit format — JSON, Protobuf, Avro — where the schema is visible, versioned, and cannot instantiate arbitrary types.

    Java
    class Session implements Serializable {
    private static final long serialVersionUID = 1L;   // declare it explicitly
    private transient String password;                  // never serialized
}

    What does transient actually do?

    Excludes the field from the default serialized form — it comes back as null/0. Use it for secrets, caches and derived values. Note it does not help with the security problem, only with what is written.

    What is the modern replacement in a Spring service?

    Jackson for JSON at the API boundary, Protobuf or Avro with a schema registry for internal messaging. Both have explicit schemas, support versioning rules, and cannot be tricked into constructing arbitrary classes.

    Inversion of Control means the framework creates and wires your objects instead of each class constructing its own dependencies. Dependency injection is how: the container supplies collaborators from outside. The benefit is testability and swappability — your service takes a PaymentGateway interface and neither knows nor cares which implementation arrives.

    Constructor injection is the correct default. It makes dependencies explicit and mandatory, allows final fields (so the object is immutable and thread-safe), fails fast at startup if something is missing, and lets you instantiate the class in a unit test with plain new — no Spring required. Since Spring 4.3, a single constructor needs no @Autowired annotation at all.

    Field injection (@Autowired on a field) is the one to argue against: fields cannot be final, the class cannot be constructed without reflection so unit tests need the container, and it hides how many dependencies a class has — which conveniently disguises a class doing too much. Setter injection is for genuinely optional dependencies only.

    Java
    @Service
class PaymentService {
    private final PaymentGateway gateway;      // final - set once, thread-safe
    private final LedgerRepository ledger;

    PaymentService(PaymentGateway gateway, LedgerRepository ledger) {  // no @Autowired needed
        this.gateway = gateway;
        this.ledger = ledger;
    }
}

var svc = new PaymentService(new FakeGateway(), new InMemoryLedger());

    How does constructor injection help you spot bad design?

    A constructor with eight parameters is visibly painful, which pressures you to split the class. Field injection hides that count, so god classes grow unnoticed.

    What if two beans of the same type exist?

    Disambiguate with @Primary on the default, or @Qualifier("name") at the injection point. You can also inject List<Handler> or Map<String,Handler> to get all of them — the idiomatic way to implement a strategy registry.

    The bean lifecycle: the container instantiates the bean, injects dependencies, calls BeanPostProcessor.postProcessBeforeInitialization, runs @PostConstruct / afterPropertiesSet, calls postProcessAfterInitialization — which is where proxies are created — and the bean is ready. On shutdown, @PreDestroy runs (for singletons only).

    Scopes: singleton (default — one instance per container, so it must be stateless or thread-safe), prototype (new instance per injection; note Spring does not manage its destruction), plus the web scopes request, session and application.

    The classic scope bug is injecting a prototype or request-scoped bean into a singleton: injection happens once, so the singleton keeps the very first instance forever. The fixes are a scoped proxy (@Scope(value="request", proxyMode=TARGET_CLASS)), or injecting an ObjectProvider/Provider and asking for a fresh instance each time.

    Java
    @Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
class RequestContext { private String traceId; }

@Service
class Singleton {
    private final ObjectProvider<Prototype> provider;   // fresh instance per call

}

    Why is BeanPostProcessor worth knowing?

    It is the extension point where Spring itself implements AOP — @Transactional, @Async and @Cacheable proxies are all created there. Understanding it explains why those annotations behave the way they do.

    Every request shares it. A mutable field on a @Service is a data race and a cross-request data leak. Keep singletons stateless, or make state explicitly thread-safe.

  • J94

    A @Configuration class is not a plain object — Spring subclasses it with CGLIB at runtime. That proxy intercepts calls to @Bean methods so that calling one from another method in the same class returns the existing singleton from the container instead of executing the method again.

    Without that interception, @Bean A a(){ return new A(b()); } and @Bean B b(){...} would create two different B instances — one for the container, one for A. Interception is what makes inter-bean references behave as you expect. This mode is called full configuration.

    Set @Configuration(proxyBeanMethods = false) — "lite" mode — when your @Bean methods never call each other. It skips the CGLIB subclass and speeds up startup, which is why Spring Boot's own auto-configurations use it. The tradeoff is that inter-bean calls then create new instances, so you must inject dependencies as method parameters instead.

    Java
    @Configuration
class AppConfig {
    @Bean A a() { return new A(b()); }   // proxied: returns the singleton b
    @Bean B b() { return new B(); }
}

@Configuration(proxyBeanMethods = false)   // faster startup, no interception
class LiteConfig {
    @Bean A a(B b) { return new A(b); }     // take it as a parameter instead
    @Bean B b() { return new B(); }
}
    Follow-ups they will ask

    Why can a @Configuration class not be final?

    CGLIB creates a subclass, and you cannot subclass a final class. The same applies to final @Bean methods and to any class Spring needs to proxy for AOP — a real gotcha with Kotlin, where classes are final by default.

    How do you know which mode you are in?

    proxyBeanMethods = true (the default) is full mode. If you see two instances of a bean you expected to be a singleton, someone set it to false and kept an inter-bean call.

  • J95

    A circular dependency is A needing B while B needs A. Spring can resolve it for setter/field injection using a three-level cache of singletons: it instantiates A, puts an early reference to the half-built A into the cache, creates B (which gets that early reference), then finishes injecting A.

    It cannot resolve it for constructor injection, because neither object can be constructed without the other already existing. Since Spring Boot 2.6 circular references are disallowed by default and the application fails to start.

    Treat that failure as a design signal, not an obstacle. A cycle almost always means the two classes share a responsibility that belongs in a third. The legitimate fixes are: extract the shared logic into a new bean; break the cycle with an event (one side publishes, the other listens); or, as a last resort, @Lazy on one injection point so a proxy is injected and resolution is deferred. Setting spring.main.allow-circular-references=true is hiding the problem.

    Java
    // fails to start - and that is correct feedback
@Service class A { A(B b) {} }
@Service class B { B(A a) {} }

// fix 1: extract the shared responsibility
@Service class A { A(Shared s) {} }
@Service class B { B(Shared s) {} }

// fix 2 (last resort): defer with a proxy
@Service class A { A(@Lazy B b) {} }
    Follow-ups they will ask

    What are the three levels of the singleton cache?

    singletonObjects (fully initialized), earlySingletonObjects (instantiated but not fully injected), and singletonFactories (factories that can produce an early reference, which is also where a proxy gets created if AOP is involved).

    Why does @Lazy work?

    It injects a proxy instead of the real bean; the real bean is resolved on first method call, by which time both are constructed. It works, but it hides the cycle rather than fixing it.

Secrets belong in a vault or environment variables, never in a committed YAML file.

    How do you keep secrets out of config?

  • J98

    A request enters through the servlet filter chain, reaches the DispatcherServlet, which consults HandlerMapping to find the controller method, then HandlerAdapter invokes it. Argument resolvers build the parameters (@RequestBody via an HttpMessageConverter, @PathVariable, @RequestParam), and on the way out a message converter serializes the return value.

    Filters vs interceptors is a frequent question. Filters are servlet-level: they see every request including static resources and errors, run outside Spring's exception handling, and are where Spring Security lives. Interceptors are Spring MVC-level: they run after handler mapping, so they know which controller method will run — better for handler-specific concerns like auditing or timing an endpoint.

    @ControllerAdvice centralizes exception handling. Map each exception type to a status and a stable error body — ideally RFC 9457 application/problem+json. Never let a raw exception reach the client: stack traces leak internals, and inconsistent error shapes break every consumer.

    Java
    @RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(NotFoundException.class)
    ProblemDetail notFound(NotFoundException e) {
        var p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        p.setType(URI.create("https://api.acme.com/errors/not-found"));
        return p;
    }
    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception e) {
        log.error("unhandled", e);                       // log detail server-side
        return ProblemDetail.forStatusAndDetail(          // return nothing sensitive
                HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}
    Follow-ups they will ask

    Why can a filter not use @ControllerAdvice?

    Filters run before the DispatcherServlet, so an exception thrown there never reaches Spring's exception resolvers. You handle it in the filter or via the container's error page — which is why Spring Security has its own entry-point and access-denied handlers.

    Where would you put request logging and correlation ids?

    A filter, so it covers every request including ones that never reach a controller, and so the correlation id is in the MDC before anything else logs.

    Bean Validation (JSR-380) is declarative constraint checking: annotate the DTO (@NotBlank, @Size, @Email, @Positive, @Past) and put @Valid on the controller parameter. A violation throws MethodArgumentNotValidException before your method body runs.

    Two mechanics worth knowing: validation groups let one DTO carry different rules for create versus update (id required on update, forbidden on create), and a custom ConstraintValidator handles domain rules — a valid IFSC code, a supported currency — keeping them declarative and reusable.

    The design point is the error contract. The default Spring error body is not good enough for an API: return a stable, machine-readable shape listing every field error at once, not just the first, so a client can highlight all of them. And validate at the boundary — do not let unvalidated data reach your domain.

    Java
    record CreateOrder(
        @NotBlank String customerId,
        @NotEmpty List<@Valid Line> lines,       // cascades into each element
        @Positive BigDecimal total) {}

@PostMapping("/orders")
Order create(@Valid @RequestBody CreateOrder req) { ... }

    var errors = e.getBindingResult().getFieldErrors().stream()

            .toList();
    var p = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
    p.setProperty("errors", errors);       // all failures, not just the first

    Difference between @Valid and @Validated?

    @Valid is the JSR-380 annotation and supports cascading into nested objects. @Validated is Spring's, adds group support, and on a class enables method-level validation via a proxy.

    Should entities carry validation annotations?

    Validate DTOs at the boundary. Entities may carry constraints as a last line of defence, but relying on them means the failure surfaces at flush time, deep inside a transaction, with a much worse error message.

  • J100

    @Transactional is implemented by an AOP proxy. Spring wraps your bean; the proxy starts a transaction before the method and commits or rolls back after. Everything surprising about it follows from that one fact.

    Self-invocation does not work. If method a() calls this.b(), the call goes directly to the target object and never through the proxy — so @Transactional on b() is silently ignored. Same reason it does nothing on private, final, or static methods. Fixes: move b() to another bean, or self-inject.

    Two more essentials. Rollback rules: by default Spring rolls back on RuntimeException and Error only — a checked exception commits unless you write rollbackFor = Exception.class. Propagation: REQUIRED (default) joins an existing transaction; REQUIRES_NEW suspends it and opens a second one on a different connection, which can deadlock against the first if it touches the same rows. And never make a remote call inside a transaction — you hold a database connection for the duration of someone else's outage.

    Java
    @Service
class OrderService {
    @Transactional
    public void placeOrder(Order o) {
        save(o);
        audit(o);        // self-invocation: @Transactional on audit() is IGNORED
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void audit(Order o) { ... }
}

// checked exception commits by default
@Transactional(rollbackFor = Exception.class)
public void risky() throws IOException { ... }
    Follow-ups they will ask

    How do you make an audit record survive a rollback of the main transaction?

    Put it in a separate bean with REQUIRES_NEW (so it commits independently), or publish an event and write it after commit with @TransactionalEventListener(phase = AFTER_COMMIT). Calling it in the same transaction guarantees it disappears with the rollback.

    What does @Transactional(readOnly = true) buy you?

    Hibernate skips dirty checking and can avoid taking a snapshot of loaded entities, and some drivers route to a read replica. It is a meaningful optimization on read-heavy endpoints and documents intent.

  • J101

    The persistence context (the EntityManager, one per transaction) is a first-level cache and a unit of work. Entities have four states: transient (new, unknown), managed (tracked by the context), detached (was managed, context closed), removed (scheduled for delete).

    Dirty checking is the consequence people forget: while an entity is managed, changing a field is enough — Hibernate compares against the snapshot it took at load and issues an UPDATE at flush. You do not call save(). That is powerful and also a trap: an accidental setter inside a transaction writes to the database.

    Flush is not commit. Hibernate flushes automatically before a query that might be affected by pending changes, and at commit. Understanding this explains why your INSERT appears at an unexpected point, and why flush() then clear() in a batch loop is necessary — otherwise the context accumulates every entity and dirty-checks them all on each flush, turning a batch job quadratic.

    Java
    @Transactional
void rename(Long id, String name) {
    Order o = repo.findById(id).orElseThrow();
    o.setName(name);            // managed - dirty checking issues the UPDATE
}                               // no save() call needed

// batch insert without exhausting the persistence context
for (int i = 0; i < rows.size(); i++) {
    em.persist(rows.get(i));
    if (i % 50 == 0) { em.flush(); em.clear(); }
}
    Follow-ups they will ask

    Why does the first-level cache mean two findById calls hit the DB once?

    Within one persistence context the entity is returned from the context by identity — and both calls return the same object instance. That identity guarantee is also why == works for entities inside one transaction.

    What is the danger of a long-running transaction?

    It holds a connection and database locks, and in Postgres it prevents vacuum from cleaning up rows newer than its snapshot, causing table bloat. Keep transactions short and never wrap user think-time or remote calls in one.

  • J102

    N+1 is the single most common ORM performance bug: one query loads N parents, then accessing a lazy association fires one query per parent. 200 orders becomes 201 queries, each with network round-trip latency. It usually passes tests (10 rows) and dies in production (10,000).

    Diagnose it by logging SQL and counting — spring.jpa.properties.hibernate.generate_statistics=true, or a datasource-proxy that asserts query counts in tests. Never assume; measure. The tell is a burst of identical queries differing only in the id parameter.

    The fixes, in order of preference: a projection/DTO query that selects exactly what you need in one statement; JOIN FETCH or @EntityGraph to load the association eagerly for that query only; @BatchSize to turn N queries into N/batch queries with an IN clause. Do not fix it by setting FetchType.EAGER on the mapping — that makes every query everywhere load the association, trading one problem for a worse one. And note JOIN FETCH with pagination cannot paginate in SQL; Hibernate warns and paginates in memory.

    Java
    // N+1: one query for orders, then one per order for lines
List<Order> orders = repo.findAll();
orders.forEach(o -> o.getLines().size());

// fix A: fetch join for this use case only
@Query("select distinct o from Order o join fetch o.lines where o.status = :s")
List<Order> findWithLines(@Param("s") Status s);

// fix B: entity graph
@EntityGraph(attributePaths = "lines")
List<Order> findByStatus(Status s);

// fix C: batching - N queries become N/50
@BatchSize(size = 50) @OneToMany(mappedBy = "order") List<Line> lines;
    Follow-ups they will ask

    Why is EAGER on the mapping considered an anti-pattern?

    It is a global decision made for a local problem. Every query that touches the entity now joins or issues extra selects, including ones that never need the association — and you cannot turn it off per query, whereas LAZY can always be fetched on demand.

    What is the MultipleBagFetchException?

    Fetch-joining two List collections at once produces a cartesian product Hibernate refuses to build. Fix by making them Sets, or by fetching one collection per query.

  • J103

    Optimistic locking assumes conflicts are rare. Add a @Version column; every UPDATE includes WHERE version = ? and increments it. If another transaction got there first, zero rows update and Hibernate throws OptimisticLockException. No database locks are held, so it scales well — and the caller must be prepared to retry or show a conflict.

    Pessimistic locking assumes conflicts are likely: it takes a database lock up front with SELECT … FOR UPDATE (PESSIMISTIC_WRITE), blocking other writers until commit. Correct for genuinely contended rows — seat inventory, account balances — at the cost of held locks, reduced concurrency, and deadlock risk if lock order is inconsistent.

    Choose by contention and cost of failure. A user editing a profile: optimistic, and show "someone else changed this". Two people buying the last seat: pessimistic, or a database constraint that makes overselling impossible. Always pair pessimistic locks with a lock timeout so a stuck transaction does not stall the system.

    Java
    @Entity class Account {
    @Id Long id;
    @Version long version;      // optimistic locking
    BigDecimal balance;
}

// pessimistic, with a timeout
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
@Query("select s from Seat s where s.id = :id")
Seat lockSeat(@Param("id") Long id);
    Follow-ups they will ask

    How do you retry an optimistic failure safely?

    Catch ObjectOptimisticLockingFailureException outside the transaction, reload fresh state, reapply the change, and retry with a small bounded number of attempts and jitter. Retrying inside the failed transaction cannot work — it is already marked rollback-only.

    Is optimistic locking enough for money?

    For a balance updated by a single service, yes — it prevents lost updates. For invariants spanning rows (a ledger that must balance), you also need the transaction and often a database constraint. Never rely on a read-then-write in application code without one of these.

  • J104

    LazyInitializationException means you touched a lazy association after the persistence context closed — typically in the controller or during JSON serialization, after the @Transactional service method returned. The proxy has no session to load from, so it throws.

    Open Session In View (OSIV) makes it disappear by keeping the session open for the whole HTTP request. Spring Boot enables it by default. It is a bad fix: it holds a database connection for the entire request including view rendering and any remote call, so under load the connection pool is exhausted by requests doing no database work — and it silently reintroduces N+1 during serialization, invisible to your service-layer tests.

    The right fix is to decide what you need while the transaction is open: fetch it explicitly with a fetch join or entity graph, and map to a DTO inside the service. Then set spring.jpa.open-in-view=false and let any remaining LazyInitializationException tell you about a genuinely missing fetch plan.

    Java
    // application.yml
// spring.jpa.open-in-view: false

@Transactional(readOnly = true)
public OrderDto get(Long id) {
    Order o = repo.findWithLines(id).orElseThrow();   // fetch plan is explicit
    return OrderDto.from(o);                          // map inside the transaction
}
// the controller returns a DTO - nothing lazy escapes the transaction
    Follow-ups they will ask

    Why is OSIV on by default if it is harmful?

    It makes simple demos and tutorials work without a fetch plan. Spring Boot even logs a warning about it at startup. For a production service, turning it off is the standard recommendation.

    What breaks immediately when you disable it?

    Any endpoint relying on lazy loading during serialization. That is the point — each failure marks a place where the fetch plan was implicit and unbounded, and you fix them with explicit queries and DTOs.

    Spring Data generates implementations from interfaces. Derived queries parse the method name (findByStatusAndCreatedAtAfter) — convenient, but past three or four conditions the names become unreadable and you should switch to @Query (JPQL) or a Specification.

    Projections are the highest-value feature for performance. Returning a full entity to render three fields loads and dirty-checks everything; an interface projection generates a narrow SELECT, and a DTO/constructor projection returns a plain object with no persistence-context overhead at all. Reaching for a projection is often a bigger win than any index.

    Specifications build type-safe dynamic predicates for filter/search endpoints — composable with and/or rather than string-concatenating JPQL. And know the pagination cost: Page runs an extra COUNT query on every call, which on a large filtered table can dominate. Use Slice when the UI only needs "is there a next page".

    Long getId(); BigDecimal getTotal(); String getStatus();
}

@Query("select new com.acme.OrderDto(o.id, o.total) from Order o where o.status = :s")

    When do you drop to a native query?

    Database-specific features — window functions, CTEs, JSONB operators, INSERT … ON CONFLICT — or a query the JPQL translator makes slow. Accept that you lose portability and that the result must be mapped explicitly.

    How do you keep a search endpoint from becoming an unbounded scan?

    Require at least one selective filter, enforce a maximum page size, use keyset pagination for deep pages, and make sure the specification's predicates match an index. An unbounded Specification endpoint is a denial-of-service waiting to happen.

  • J106

    HikariCP is Spring Boot's default connection pool. Opening a database connection is expensive (TCP, TLS, authentication), so the pool keeps a small set open and hands them out. The key insight is that the pool size is a concurrency limit on your database, not a throughput dial.

    Small pools are usually right. HikariCP's own guidance is roughly connections = cores × 2 + effective spindles — often 10 to 20, not 200. A larger pool does not make the database faster; it just lets more queries contend for the same CPUs and disks, increasing every query's latency. Postgres in particular degrades sharply past a modest connection count, which is why PgBouncer exists.

    Pool exhaustion masquerades as a slow application. All threads sit in getConnection(), CPU is low, the database looks idle, and p99 explodes. Diagnose it from Hikari's metrics — active vs idle vs pending connections — and from a thread dump full of threads parked in HikariPool.getConnection. The cause is almost always a leaked connection (a transaction that never commits) or a long-running query, not an undersized pool.

    Java
    spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 3000      # fail fast rather than queue forever
      leak-detection-threshold: 20000   # log a stack trace for held connections
      validation-timeout: 2000

# expose metrics: hikaricp_connections_pending is the one that matters
    Follow-ups they will ask

    What does connection-timeout do and why set it low?

    It bounds how long a thread waits for a connection before failing. A short timeout converts a pool exhaustion into fast, visible errors and a circuit-breaker trip, instead of every request thread blocking and the whole service hanging.

    How do you size the pool alongside your thread pool?

    They must be considered together: 200 request threads in front of 20 connections means 180 threads queue. Either bound the request concurrency to something close to the pool size, or accept and monitor the queue explicitly.

    Spring Security is fundamentally a chain of servlet filters. A request passes through them in order, and each can authenticate, authorize, or short-circuit. Because it is a filter chain, it runs before the DispatcherServlet — which is why @ControllerAdvice cannot handle security failures; those go to the AuthenticationEntryPoint (401) and AccessDeniedHandler (403).

    Authentication is "who are you" — a filter extracts credentials (session cookie, Basic header, JWT), an AuthenticationProvider verifies them, and the resulting Authentication goes into the SecurityContextHolder (a ThreadLocal). Authorization is "what may you do" — URL rules in the filter chain, or method-level @PreAuthorize backed by a proxy.

    Two practical points. Order matters: the authentication filter must precede the authorization check, and a misordered custom filter silently fails open or closed. And because the context is a ThreadLocal, it does not propagate to threads you spawn — use DelegatingSecurityContextExecutor or pass the principal explicitly, or your async code runs unauthenticated.

    Java
    @Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())                       // stateless API with bearer tokens
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())                  // deny by default
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
    Follow-ups they will ask

    When is disabling CSRF correct?

    Only for a stateless API authenticated by a bearer token in a header — a browser cannot be tricked into adding that header cross-site. If you authenticate with cookies, CSRF protection is mandatory.

    Why anyRequest().authenticated() at the end?

    Deny by default. Listing what is public and requiring authentication for everything else means a newly added endpoint is secure until someone deliberately opens it — the opposite ordering fails open.

    The authorization code flow with PKCE is the standard for both web and mobile now. The client redirects the user to the authorization server with a code_challenge (a hash of a random code_verifier). The user authenticates there; the server redirects back with a short-lived code; the client exchanges that code plus the original verifier for tokens. PKCE exists so an intercepted code is useless without the verifier — which is why the old implicit flow is deprecated.

    OIDC layers identity on OAuth2: an id_token (a JWT about the user) alongside the access_token (about permissions). Validate a JWT properly: signature against the JWKS, plus iss, aud, exp, and reject alg: none and algorithm confusion. Spring's resource server does this for you — the failure mode is hand-rolled validation.

    The hard part is revocation: a JWT is valid until it expires, by design. The practical answer is short-lived access tokens (5–15 min) plus a longer refresh token with rotation and reuse detection — if an old refresh token is presented again, the whole family is revoked, because it means one was stolen. Keep a denylist by jti only for emergencies.

    Java
    # resource server: signature + claims validated against the JWKS endpoint
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://accounts.google.com
          # audiences and issuer are checked automatically

// access the validated principal
@GetMapping("/me")

    Follow-ups they will ask

    Where should a browser client store tokens?

    An httpOnly, Secure, SameSite cookie — inaccessible to JavaScript, so XSS cannot exfiltrate it. That reintroduces CSRF, handled with SameSite plus a CSRF token. localStorage is convenient and XSS-exposed; say the tradeoff explicitly rather than picking one blindly.

    What is the blast radius of a leaked signing key?

    Anyone can mint valid tokens for any user until the key is rotated and every issued token expires. Mitigate with short expiry, key rotation via JWKS with overlapping keys (kid in the header), and keys held in an HSM or KMS rather than config.

  • J109

    Spring's cache abstraction is annotation-driven: @Cacheable (return from cache or compute and store), @CachePut (always compute, always update), @CacheEvict (remove). It is backed by a pluggable CacheManager — Caffeine locally, Redis when shared across instances.

    It is proxy-based, exactly like @Transactional, so it has the identical self-invocation trap: a call to this.cachedMethod() bypasses the proxy and the cache does nothing. Same for private and final methods. This is the number one reason people say "caching isn't working".

    Other real pitfalls: the default key generator uses all parameters, so overloads and irrelevant parameters silently fragment the cache — specify key explicitly with SpEL. Caching null is on by default and can pin a negative result. There is no per-entry TTL without configuring it on the CacheManager. And use sync = true to get single-flight behaviour: without it, N concurrent misses all compute the value — a cache stampede against your database.

    Java
    @Cacheable(cacheNames = "rates", key = "#from + ':' + #to", sync = true,
           unless = "#result == null")
public Rate lookup(String from, String to) { return client.fetch(from, to); }

@CacheEvict(cacheNames = "rates", key = "#rate.from + ':' + #rate.to")
public void update(Rate rate) { repo.save(rate); }

// Redis TTL is configured on the CacheManager, not the annotation
RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofMinutes(10));
    Follow-ups they will ask

    Why not use JDK serialization for Redis cache values?

    It locks the payload to exact class versions, so a field addition breaks every cached entry across a rolling deploy, and it carries the deserialization attack surface. Configure a JSON serializer and treat the cache format as a versioned contract.

    What happens on a cache node failure?

    Every request becomes a miss and hits the database simultaneously — a cache outage becomes a database outage. Defend with sync=true, a small local L1 cache, TTL jitter, and a circuit breaker so the database is not overwhelmed.

  • J110

    On the producer side the settings that matter are acks, idempotence, and batching. acks=all plus min.insync.replicas=2 means a write is acknowledged only once it is on multiple replicas — the durability setting for financial events. enable.idempotence=true gives per-partition exactly-once producing (deduplicating retries), and it is the default on modern clients. linger.ms and batch.size trade a little latency for a lot of throughput.

    The partition key is the single most important design decision: ordering is guaranteed only within a partition, so the key determines what is ordered relative to what. For a ledger, keying by account id guarantees a single account's events are ordered while different accounts process in parallel. A null key round-robins and gives you no ordering at all.

    On the consumer side, turn off enable.auto.commit and commit manually after processing. Auto-commit commits on a timer, so a crash between the commit and the processing loses messages — a silent data-loss window. Manual commit after processing gives at-least-once, which means your handler must be idempotent. Also set max.poll.records and keep processing under max.poll.interval.ms, or the broker assumes you died and rebalances mid-batch.

    Java
    spring:
  kafka:
    producer:
      acks: all
      properties: { enable.idempotence: true }
    consumer:
      enable-auto-commit: false
      max-poll-records: 100
      isolation-level: read_committed
    listener:
      ack-mode: manual_immediate

@KafkaListener(topics = "payments", concurrency = "3")
void onMessage(PaymentEvent e, Acknowledgment ack) {
    process(e);      // must be idempotent - at-least-once delivery
    ack.acknowledge();
}
    Follow-ups they will ask

    How do you increase consumer throughput?

    Add partitions and consumers up to the partition count — a partition is consumed by exactly one consumer in a group, so consumers beyond that sit idle. Beyond that, parallelize within the consumer while preserving per-key ordering, which is considerably harder.

    What is consumer lag and why is it the key SLI?

    The offset difference between the latest message and the consumer's committed position. It is the earliest signal that your consumers cannot keep up, and it predicts a breach long before latency alarms fire. Alert on lag and on lag growth rate.

  • J111

    A poison message — one that always fails, perhaps a schema change or corrupt payload — will block a partition forever if you simply retry, because Kafka must process in offset order. That single message stops every message behind it. This is the failure mode to name.

    The standard pattern is bounded retry then dead-letter: retry a few times with backoff for transient failures, and after N attempts publish the message to a DLQ topic and commit the offset so the partition moves on. Spring Kafka's DefaultErrorHandler with a DeadLetterPublishingRecoverer implements this.

    Two refinements worth mentioning. Classify the exception: a deserialization or validation failure will never succeed, so send it straight to the DLQ without retries, while a downstream timeout deserves them. And for longer waits use separate retry topics with increasing delays rather than blocking the consumer thread — blocking retries hold up the partition and can trigger a rebalance by exceeding max.poll.interval.ms. Finally, a DLQ nobody monitors is just deleting data: alert on its depth and have a documented replay procedure.

    Java
    @Bean
DefaultErrorHandler errorHandler(KafkaTemplate<String,Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template,
            (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
    var handler = new DefaultErrorHandler(recoverer,
            new ExponentialBackOffWithMaxRetries(3));
    handler.addNotRetryableExceptions(                 // never going to succeed
            DeserializationException.class, ValidationException.class);
    return handler;
}
    Follow-ups they will ask

    What do you record alongside the message in the DLQ?

    The original topic, partition, offset, the exception class and message, a stack trace, and a timestamp — Spring adds these as headers. Without them a DLQ message is unactionable.

    How do you replay a DLQ safely?

    Fix the cause, then republish to the original topic with a consumer that reads the DLQ. Because handlers are idempotent, replaying an already-processed message is harmless — which is exactly why idempotency is non-negotiable.

    Structure tests as a pyramid. Most should be plain unit tests — no Spring, just new and a fake. They run in milliseconds, which is what keeps the suite usable. Reserve @SpringBootTest (which starts the whole context) for a handful of end-to-end paths; it is slow and its context caching is easily defeated by inconsistent test configuration.

    Use slices for the middle layer: @WebMvcTest loads only the web layer with MockMvc, @DataJpaTest only JPA with a transactional rollback per test. Know @Mock (plain Mockito, no context) versus @MockBean (replaces a bean in the Spring context — and creates a new context cache entry, so overusing it slows the whole suite).

    Two specifics interviewers like. Async testing: never Thread.sleep — use Awaitility to poll a condition with a timeout, which is both faster and non-flaky. Testcontainers: run the real Postgres, Kafka or Redis in Docker for integration tests. Testing against H2 when you run Postgres in production means dialect differences, missing JSONB, and different locking behaviour all pass locally and fail in production.

    Why does @MockBean slow the suite down?

    Each distinct set of mocked beans produces a different application context, and Spring caches contexts by configuration. Ten variations means ten context startups. Prefer constructor-injected fakes in unit tests.

    What should you not mock?

    Types you do not own. Mocking a third-party client encodes your assumption about its behaviour; if the assumption is wrong the test still passes. Wrap it in your own interface, mock that, and cover the real thing with one integration test.

  • J113

    Both Maven and Gradle resolve transitive dependencies, but with different conflict rules, and that difference causes real bugs. Maven uses nearest-wins: the version at the shallowest depth in the tree, with declaration order breaking ties. Gradle uses highest-wins: the newest version requested by anyone. The same dependency graph can therefore produce different runtime versions in the two tools.

    The diagnostic tools are mvn dependency:tree and gradle dependencies — learn to read them, because "NoSuchMethodError at runtime" is almost always two versions of a library where the resolved one is not what you expected. Pin versions centrally with a BOM (dependencyManagement in Maven, a platform in Gradle); the Spring Boot BOM exists precisely so the dozens of libraries it pulls in stay mutually compatible.

    Shading (relocating packages into your own namespace at build time) solves the case where you and a dependency need incompatible versions of the same library. It is a library-author tool; using it in an application usually means the dependency graph needs cleaning instead.

    Java
    mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind
mvn dependency:analyze          # declared-but-unused, used-but-undeclared
gradle dependencyInsight --dependency jackson-databind

<dependencyManagement><dependencies><dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-dependencies</artifactId>
  <version>3.3.0</version><type>pom</type><scope>import</scope>
</dependency></dependencies></dependencyManagement>

    What is NoSuchMethodError telling you?

    The class was found but not the method — you compiled against one version and are running against another. It is a dependency-resolution problem almost every time, not a code problem.

    How do you keep the graph healthy over time?

    Use the BOM, run dependency:analyze in CI to catch undeclared transitive use, and scan with the OWASP dependency-check or GitHub Dependabot so CVEs in transitive dependencies surface before an auditor finds them.

    Patterns are worth far more when you can point at them in code you already use, rather than reciting definitions. That is what separates a memorized answer from a fluent one.

    In the JDK: Decorator throughout java.io (new BufferedReader(new InputStreamReader(in))); Strategy in Comparator; Factory Method in Collection.iterator() and List.of; Builder in StringBuilder, Stream.Builder, HttpRequest.newBuilder(); Observer in Flow/listeners; Adapter in Arrays.asList; Singleton in enums.

    Which pattern is most over-applied?

    Singleton — usually a global mutable variable in disguise, which destroys testability. In a Spring application you almost never need it: a singleton-scoped bean gives you one instance with none of the drawbacks.

  • J115

    SRP — a class should have one reason to change. OCP — open for extension, closed for modification. LSP — a subtype must be usable wherever the supertype is. ISP — many small interfaces beat one fat one. DIP — depend on abstractions, and let the high-level policy own the interface.

    In practice SRP and DIP earn their keep constantly: splitting a class that does validation, persistence and notification makes each testable, and depending on a PaymentGateway interface lets you swap providers and fake it in tests.

    The senior signal is knowing when not to apply them. OCP and ISP are the most over-applied: an interface with exactly one implementation, created "for flexibility", is pure indirection — it adds a file, obscures navigation, and you will change both together anyway. Introduce the abstraction when the second implementation actually arrives, or when you need a test seam at a real boundary. Being able to argue against a principle, with a concrete example, is what distinguishes an Software Engineer answer from a recited one.

    Java
    // before: three reasons to change in one class
class OrderService { void place(Order o){ validate(o); repo.save(o); email.send(o); } }

// after: SRP + DIP - each collaborator is an abstraction owned by this layer
class OrderService {
    private final OrderValidator validator;
    private final OrderRepository repository;   // interface, implemented by JPA
    private final OrderNotifier notifier;       // interface, implemented by email
    void place(Order o){ validator.check(o); repository.save(o); notifier.placed(o); }
}
    Follow-ups they will ask

    Give an example of over-applying OCP.

    A StrategyFactory with an enum, an interface and one implementation, built for a rule that has never changed in three years. Every new developer must read four files to follow one branch. A plain if would have been better until a second rule appeared.

    How does SRP relate to testability?

    Directly. A class with one responsibility has few collaborators, so its tests need few fakes and assert one thing. If a test needs six mocks, the class has six responsibilities.

    Library design is judged by how hard it is to misuse. Make the common case one line and the complex case possible. Prefer static factories with meaningful names (Money.ofMinor, Duration.ofSeconds) over a set of overloaded constructors that differ only in parameter types — names document intent and can return cached or subtype instances.

    On nulls: never return null for a collection (return an empty one), use Optional as a return type where absence is meaningful, and validate parameters at the boundary with Objects.requireNonNull so the failure points at the caller rather than surfacing three frames deeper. Be explicit about nullability in the signature and the javadoc.

    On compatibility, know what breaks: adding an abstract method to an interface (use default), changing a return type, widening a thrown checked exception, renaming an enum constant that is persisted, and changing behaviour that callers depend on. Adding an overload can even break source compatibility by creating ambiguity. Version with semver, deprecate with @Deprecated(since=, forRemoval=) and a migration note, and give consumers a real window before removal.

    Why is returning null from a collection-returning method bad?

    It forces every caller to null-check, and one who forgets gets an NPE far from the cause. An empty collection composes correctly with loops and streams and needs no special case — and List.of() costs nothing.

    What is the cost of a badly chosen public API?

    You keep it forever. Every consumer depends on it, so fixing it means a major version and a migration for everyone. That asymmetry is why the smallest possible public surface is the right default.

    Injection — the top risk, and in Java almost always SQL built by string concatenation. The fix is parameter binding (PreparedStatement, JPQL parameters, Spring Data). Dynamic ORDER BY cannot be parameterized, so validate it against an allowlist of column names — never interpolate user input into SQL structure.

Always bind to a request DTO containing only the fields a client may set, and map explicitly.     Deserialization — never deserialize untrusted Java-serialized data (see J91); with Jackson, keep polymorphic typing off unless you allowlist subtypes, because enableDefaultTyping has produced multiple RCEs. Secrets — from environment or a vault, never in committed YAML, never in logs, and rotated.
